# 99 综合项目：打通从模型到生产系统的闭环

## 99.0 项目总则

本章是全课程的毕业设计。三个项目分别对应课程的三条主线：**系统闭环**（项目一，必做）、**LLM 服务的性能工程**（项目二）、**发布风险管理**（项目三）。项目一必须完成；项目二、三至少完成一个，时间充裕建议全做。

通用要求（三个项目都适用）：

1. **单一 Git 仓库**：所有代码、配置、文档、实验报告入库；`README` 说明如何在 30 分钟内从零跑通；
2. **一切数字有出处**：报告中的每个延迟/吞吐/成本数字都注明测试环境（硬件、版本、时间）与测量方法（预热、次数、统计量）——遵守第 1 章 1.6 节与第 2 章 2.9 节的基准方法论；
3. **失败演练优先**：本课考核的不是"能跑通"，而是"坏了知道为什么、有预案"——每个项目都包含一个注入故障的环节；
4. 建议总工作量：项目一 15–20 小时，项目二 8–12 小时，项目三 6–8 小时。

## 99.1 项目一（必做）：最小 MLOps 闭环——训练 → 导出 → 服务 → 监控 → 自动重训

### 99.1.1 项目目标

为一个小型分类/回归任务（建议：[数据工程](/xiaoshus-blog/textbooks/ai/engineering/data-engineering/00/) 项目产出的数据集，或 sklearn 自带的合成任务）搭建一条完整的持续训练闭环，并对它注入漂移，观察系统自愈。

### 99.1.2 系统规格（必须实现）

```
模拟流量生成器 ─▶ FastAPI 服务 (加载注册表 production 版模型) ─▶ 预测日志 (CSV/SQLite)
        │                                                              │
        ▼                                                              ▼
  漂移注入开关(周级别)                                    监控器: PSI(逐特征) + 预测分布
                                                                     │ PSI ≥ 0.25
                                                                     ▼
                                            重训流水线: 数据校验 → 训练 → champion/challenger 门禁
                                                                     │ 通过
                                                                     ▼
                                             最小模型注册表 (第4章案例2可扩展) → 服务热加载新版本
```

### 99.1.3 功能要求

1. **服务**（第 2 章 2.7 节为骨架）：`/predict`、`/health`、模型版本号随响应返回；
2. **模拟流量**：每秒 N 条请求（可配置），其中特征分布受"周数"参数控制——第 1–3 周平稳，第 4 周起注入渐进漂移（均值每周 +0.15σ，或某特征突变为另一分布）；
3. **监控器**：离线批处理脚本，每小时（模拟）聚合预测日志，计算各特征 PSI 与预测正类率，输出周报 CSV；PSI ≥ 0.25 打印 ALARM（第 3 章）；
4. **重训流水线**：被 ALARM 触发后自动运行：数据校验（schema + 范围）→ 用含新数据的数据集重训 → 在冻结评估集上与现任模型对照（第 4 章 4.2 模型校验）→ 通过则注册并热加载；
5. **闭环证据**：一段运行日志显示"漂移注入 → ALARM → 自动重训 → 服务版本号变化 → PSI 回落"的完整时间线。

### 99.1.4 任务分解（建议顺序）

1. 搭服务 + 流量生成器，先让"静态模型"跑起来（对应第 2 章）；
2. 加预测日志与监控器（第 3 章），手动注入漂移验证 ALARM 能响；
3. 写重训脚本 + 注册表门禁（第 4 章），手动触发验证版本切换；
4. 把 2 与 3 用告警事件串起来，端到端跑通闭环；
5. 做三次对照实验：不注入漂移（不应重训）、注入漂移但新数据被污染（门禁应拒绝）、正常漂移（应重训并恢复）。

### 99.1.5 验收标准（逐条可勾选）

- [ ] `docker compose up`（或等价脚本）一条命令拉起全部组件；
- [ ] 运行报告中包含"PSI 周报表"与"版本切换时间线"两张表；
- [ ] 第 4 周起 3 个模拟周内完成自动重训，服务版本号 +1；
- [ ] 门禁拒绝测试：故意提供劣化数据集，重训产物被拒绝且现任版本不变；
- [ ] 全流程无需人工干预的录像/日志片段；
- [ ] 报告 ≤ 5 页：架构图、三次对照实验结果、已知缺陷清单。

### 99.1.6 挑战扩展（选做）

- 给服务加 p99 延迟 SLO 与多窗口燃烧率告警（第 2、3 章），并在报告中给出延迟-利用率曲线；
- 把重训流水线改写为真正的编排 DAG（Airflow 或第 4 章案例的 DAG 模拟器），支持失败重试；
- 引入影子部署：新版本先影子运行 1 个模拟周，judge 指标通过后才切流。

## 99.2 项目二：LLM 服务压测——量化档位、吞吐与长尾延迟

### 99.2.1 项目目标

在本地（GPU 或 CPU）部署一个量化小模型（建议 1B–7B 级别，如 Qwen2.5-1.5B/7B、Llama-3.2-1B/3B 或 SmolLM），用 vLLM 或 llama.cpp 完成一次系统的性能对比实验，并回答"该用哪个量化档上线"。

### 99.2.2 实验设计（必须覆盖）

1. **两个量化档**：如 FP16 vs Q4_K_M（GPU/llama.cpp），或 Q8_0 vs Q4_K_M（CPU）；
2. **三组负载**：短进短出（~100/100 token）、长进短出（~1000/100）、短进长出（~100/500），各 50 条固定 prompt（含随机 seed 可复现）；
3. **三档并发**：1、8、32 路并发压测；
4. **测量指标**：吞吐（tokens/s 总量）、TTFT p50/p99、TPOT p50/p99、峰值显存/内存；
5. **质量抽查**：两个量化档在 20 条固定问题上的输出对比，人工评估并报告 3 个可感知差异样例。

### 99.2.3 任务分解

1. 环境安装与模型下载（注意磁盘与显存预算，用第 5 章 5.8 的公式预演一遍）；
2. 写压测客户端（`concurrent.futures` + OpenAI 兼容 API 或 llama.cpp server），支持并发与指标采集；
3. 跑完整矩阵（2 档 × 3 负载 × 3 并发），结果存 CSV；
4. 画图：并发-吞吐曲线、TTFT 分布箱线图；写 ≤ 4 页报告并给出选型结论。

### 99.2.4 验收标准

- [ ] 结果表完整覆盖 2×3×3 = 18 个组合，每个数字可复现（命令 + seed）；
- [ ] 报告含"吞吐-并发"曲线，并能解释曲线为何在高档并发趋平（用第 2 章利用率与第 5 章带宽受限论证）；
- [ ] 显存实测值与 5.8 公式的预测值对照，误差 > 20% 时给出解释；
- [ ] 质量抽查含具体样例对照，不做"差不多"式的模糊结论。

### 99.2.5 挑战扩展（选做）

- 打开/关闭 prefix caching 对比长系统提示词场景的 TTFT；
- 实现一个简化 continuous batching 模拟器（第 5 章案例 2 扩展：加入到达时间与真实输出长度分布），用实测的输出长度分布拟合后预测端到端吞吐，与引擎实测对照。

## 99.3 项目三：一次带回滚演练的安全灰度上线

### 99.3.1 项目目标

为一个已有模型（项目一的模型即可）设计并实施一次 v2 模型的灰度上线，包含完整的门控判定与**真实执行的回滚演练**。

### 99.3.2 功能要求

1. **v2 模型**：与 v1 有可测差异（换超参/换特征子集/故意用劣化数据训练一份"坏模型"用于回滚演练）；
2. **路由层**：按 user_id 哈希把流量分为 1%/5%/25%/100% 四档（同一用户粘性分桶，第 2 章 2.6）；
3. **门控指标**：错误率、p99 延迟（guardrail），离线 AUC（业务指标）；预先写明判定规则与回滚触发条件（文档化，不是临场决定）；
4. **影子阶段**：v2 先影子运行，报告其线上预测分布与 v1 的差异；
5. **回滚演练**：在灰度 25% 时把 v2 换成"坏模型"（或在流量层注入错误），触发自动回滚，测量**从异常开始到 100% 流量回到 v1 的恢复时间（MTTR）**。

### 99.3.3 任务分解

1. 写灰度路由中间件与分桶持久化；
2. 写门控判定脚本（输入：两版本的指标日志；输出：继续/暂停/回滚 的决策与依据）；
3. 设计并撰写《发布预案》文档（含"谁在什么条件下按什么按钮"）；
4. 正常灰度走一遍 → 注入故障演练回滚 → 复盘 MTTR 与预案缺陷。

### 99.3.4 验收标准

- [ ] 《发布预案》先行：门控指标、阈值、每档流量、回滚触发条件全部书面化；
- [ ] 同一用户在整个灰度期间始终看到同一版本（日志可验证）；
- [ ] 回滚演练的 MTTR 有实测数字，且恢复后 1% 流量无残留在 v2（粘性分桶正确性）；
- [ ] 复盘报告指出至少 2 个演练暴露的预案缺陷及修正。

### 99.3.5 挑战扩展（选做）

- 用《实验设计与评估》的功效分析反推：要在 25% 灰度档以 80% 功效检出 1% 的转化率差异，最少需要多少请求与多少天？用模拟流量验证样本量估算。
- 给门控脚本加上第 3 章的多窗口燃烧率告警逻辑，模拟"毛刺不触发、持续劣化触发"。

## 99.4 提交与评审

- **提交物**：仓库链接 + 每个项目一份 ≤ 5 页报告（PDF 或 Markdown）+ 关键演示的录屏或完整日志；
- **评分建议**：功能完整 40%、实验方法与数字可复现 30%、失败演练与预案质量 20%、报告表达 10%；
- **自问清单**（评审前逐条过）：每个数字有出处吗？回滚真的演练过吗？门禁拒绝过坏模型吗？README 让陌生人 30 分钟跑通吗？

## 99.5 与前后章节的联系

- 项目一串联第 1–4 章的导出、服务、监控、注册表全链路，是本课的"系统总装"；
- 项目二把第 1 章的量化与基准方法论、第 2 章的压测与容量分析、第 5 章的 LLM 服务特性拧成一个真实实验；
- 项目三把第 2 章的灰度与回滚、第 3 章的告警、第 4 章的门禁、《实验设计与评估》的统计功效合成为一次完整的风险管理实践；
- 完成任意两个项目后，你在 [数据工程](/xiaoshus-blog/textbooks/ai/engineering/data-engineering/00/) 构建的数据管道、本课程构建的服务与流水线，即可合并为一份可以写进简历的"端到端 ML 系统"作品。
