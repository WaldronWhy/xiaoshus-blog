# 第 4 章 MLOps 平台与全流程 CI/CD

> **本章定位**：前三章分别解决了"模型出厂、模型上岗、模型运维"，本章把它们装配成一个**自动化运转的系统**：CI/CD/CT 三条流水线、编排器、特征商店、模型注册表，以及所有工程师都绕不开的另外三件事——成本、合规与安全。前置要求：第 1–3 章全部内容、[Python·第 7 章](/xiaoshus-blog/textbooks/ai/programming/python/07/)（测试与工程规范）、[数据工程·第 3 章](/xiaoshus-blog/textbooks/ai/engineering/data-engineering/03/)（集群与调度基础）。

5. 用一个决策框架在"托管云平台 / 开源自建 / 纯手搓"之间做选择，并完成 GPU spot 实例的成本期望计算；

## 4.1 ML 项目完整生命周期回顾

从 [机器学习·第 1 章](/xiaoshus-blog/textbooks/ai/ai-core/machine-learning/01/) 起你接触的"建模"，只是下面这个环上的一小段：

```
① 界定问题与成功指标 ─▶ ② 数据获取与校验 ─▶ ③ 特征工程 ─▶ ④ 训练与实验
       ▲                                                        │
       │                                                        ▼
 ⑦ 监控与漂移检测 (第3章) ◀── ⑥ 监控上线 (第2章) ◀── ⑤ 导出与优化 (第1章)
       │                                                        │
       └────────────── 新数据/新问题/新想法驱动下一轮迭代 ◀────────┘
```

第 1–3 章已经把这个环走了一遍。本章的任务是把这个环**从"人肉驱动"变成"机器驱动"**：每次循环不再依赖某个人记得跑哪个脚本、按什么顺序、检查什么指标。

有一个观念转变是本章一切讨论的前提：在 ML 项目里，**"实验"（一次训练 = 特定数据 + 特定代码 + 特定超参 + 特定产出的组合）是流水线的核心对象**，而不是"代码提交"。传统 CI/CD 追踪 commit；ML 流水线必须同时追踪数据版本（[数据工程·第 4 章](/xiaoshus-blog/textbooks/ai/engineering/data-engineering/04/) 的 DVC）、代码版本、超参与环境、产出工件与指标——这套四元组对应关系的记录称为**血统（lineage）**，是事后归因（"上周模型为什么突然变差"）的唯一线索。

## 4.2 CI/CD 在 ML 中的特殊之处

传统 CI（持续集成）= 代码合并前自动跑单元测试；传统 CD（持续交付/部署）= 通过测试的代码自动进入发布流程。ML 系统在此基础上多出两条判断与一条流水线。

### 4.2.1 三条流水线

- **CI/CD（管代码与流水线本身）**：与软件 CI 相同 + ML 特有测试（见下）；部署对象除了服务代码，还包括**训练流水线本身的修改**（改特征定义 → 重建并部署新流水线，这是 Google 成熟度 2 级的标志）。
- **CT（管数据到模型）**：第 3 章 3.5 节的持续训练流水线——由新数据或漂移触发，产出新模型候选。
- **CD（管模型工件）**：模型候选过门禁后，自动走第 2 章的灰度/影子/回滚发布路径。

### 4.2.2 三类 ML 特有测试门禁

1. **数据校验（data validation）**：进流水线的先过数据关。schema 校验（类型、缺失率、值域）+ 分布校验（与基准比 PSI，见第 3 章）。代表工具 TFDV 的思想就是"把 schema 声明为代码、把校验做成流水线步骤"。
2. **模型校验（model validation）**：第 3 章的 champion/challenger 对照——新模型必须在冻结评估集上不输现任，且满足最低指标线（如 AUC ≥ 0.85）。
3. **模型行为测试（behavioral testing）**：把软件测试的"不变量"思想搬到模型上（Ribeiro 等人的 CheckList 工作，ACL 2020 最佳论文）：
   - **不变性测试（invariance）**：把"北京"换成"上海"，情感分析结果不应变；
   - **方向性测试（directional）**："这部电影非常好"的情感得分应高于"这部电影还行"；
   - **最小功能测试（MFT）**：一批带已知答案的模板样例必须全对。

   这些测试捕获的是"指标好看但模型荒谬"的行为缺陷，是 [Python·第 7 章](/xiaoshus-blog/textbooks/ai/programming/python/07/) 中"测试用例即规格说明"思想在概率型输出上的延伸——只是断言从"精确相等"放宽为"统计上合理"（如"概率差 > 0.1"、"样本一致率 > 95%"）。

Breck 等人的 ML Test Score（2017）把上述所有检查整理成 28 项打分清单（数据、模型、基础设施、监控四大类），可作为团队自评模板。

## 4.3 端到端流水线编排：Airflow 与 Kubeflow 的思想

把 4.1 的环写成代码就是**编排（orchestration）**问题：任务有依赖（先校验后训练）、要重试、要补历史（backfill）、要可视。两个代表系统给出了两种抽象：

**Apache Airflow**：**工作流即 Python 代码**。用户定义 DAG（有向无环图），每个节点是一个 operator（如 `PythonOperator`、`SparkSubmitOperator`）；调度器按计划时间与依赖关系触发，支持重试、超时、SLA 告警、backfill。最适合以数据工程为中心的定时批处理（训练流水线的"外环"）。

**Kubeflow Pipelines**：**每一步 = 一个容器镜像**。流水线在 Kubernetes 上运行（底层是 Argo Workflows），每步的输入输出是工件（artifact），存储在对象存储上，步骤执行记录写入 **ML Metadata** 数据库——血统追溯内建于设计。最适合以实验为中心的 ML 训练（"内环"），且天然要求每步容器化、可复现。

跨系统的通用设计法则（比工具重要）：

1. **任务幂等**：同输入重跑必得同结果——重试机制的安全前提；
2. **不传内存状态**：步骤间只通过持久化工件（文件/数据库）传递数据，任何一步崩溃都能独立重跑；
3. **小步快跑**：一个步骤 = 一个明确职责 + 明确的输入输出 schema；
4. **失败可见**：每步的成功/失败/耗时都进监控（与第 3 章的告警体系打通）。

## 4.4 特征商店与模型注册表

这两个组件是 MLOps 平台上使用频率最高、也最常被误用的两个"存储"。

**特征商店（feature store）**解决的正是第 3 章 3.6 节的"特征线一致"问题：

- **离线存储（offline store）**：历史特征表（Hive/BigQuery/Delta 类），供训练做 **point-in-time join**——为每个训练样本取"当时那个时刻"的特征值，杜绝时间穿越（在 [数据工程·第 2 章](/xiaoshus-blog/textbooks/ai/engineering/data-engineering/02/) 与其第 4 章的泄漏讨论中已强调这是评估正确性的生命线）；
- **在线存储（online store）**：低延迟 KV 存储（Redis 类），服务时毫秒级取最新特征；
- **特征定义共享**：同一份"近 7 天点击数"的定义（窗口、聚合方式、单位）离线在线共用，训练-服务偏斜从"靠自觉"变成"靠系统"。

开源代表：Feast。注意代价：多一个存储组件 = 多一份一致性运维负担，特征少、更新慢的团队用一个共享 Python 特征库可能就够了。

**模型注册表（model registry）**是模型工件的**单一事实源（single source of truth）**：

- 每个注册版本绑定：工件哈希（第 1 章导出的模型文件）、训练血统（数据版本 + 代码 commit + 超参）、评估指标、审批状态；
- 状态机：`candidate → staging → production → archived`，晋升必须过 4.2 节的门禁，支持带审批的晋升流程；
- 与部署打通：生产服务加载"production 阶段的最新版本"，**回滚 = 把状态指回旧版本**（第 2 章 2.6 节的回滚在这里落地为一次状态变更）。

开源代表：MLflow Model Registry；云厂商均有对应托管服务。4.9 案例 2 会从零实现一个最小注册表，看清它的本质其实是一组校验规则 + 一张状态表。

## 4.5 云与自建的选择框架

没有标准答案，但有结构化的决策框架。按"该问题的差异化程度 × 团队规模与迭代频率"两轴判断：

| 选项 | 代表 | 优势 | 代价 | 适合 |
|---|---|---|---|---|
| 托管平台 | SageMaker / Vertex AI / Azure ML | 开箱即用（训练/注册/端点/监控全家桶） | 厂商锁定、成本、黑盒 | 小团队快速上线、无特殊需求 |
| 开源自建 | Kubeflow + MLflow + Feast + Airflow | 可控、可迁移、可深度定制 | 平台团队工程量大（常需数人年） | 有平台团队、多模型规模化迭代 |
| 纯手搓 | 脚本 + cron + 自写服务 | 零学习成本 | 全部横切问题自己扛 | 原型、0 级成熟度足够的场景 |

两条经验法则：其一，**不要为"还没到的规模"建平台**——成熟度应匹配迭代频率（第 3 章 3.7 节的原则，这里是它的组织版）；其二，把"训练模型"这种差异化工作外包给别人做不了，把"鉴权、审计、流水线"这种无差异工作外包出去是合理的——Google 的 SRE 文化称之为"别自己造无差异的重活（undifferentiated heavy lifting）"。混合路线（云上托管存储 + 自有编排）在数据敏感型组织中最常见。

## 4.6 成本工程

GPU 是 ML 公司最贵的资产，成本工程值得单独一章的篇幅，这里给出核心框架。

**指标一：GPU 利用率**。训练任务常见利用率 30–50%（数据加载瓶颈、同步等待），治理手段：数据预取（见 [深度学习·第 8 章](/xiaoshus-blog/textbooks/ai/ai-core/deep-learning/08/)）、更快的存储、混合精度。服务场景靠第 2 章的 dynamic batching + 实例副本数调节；多模型共享 GPU 可用 **MIG**（Multi-Instance GPU，把单卡硬件切分为多个隔离实例）或时间片轮转。

**指标二：摊销成本**。一次推理请求的真实成本：

$$
c_{\text{req}} = \frac{\text{每小时全部基础设施成本}}{\text{每小时吞吐}}
$$

它是"模型该多大"的最终裁判：A 模型准确率高 0.5% 但 $c_{\text{req}}$ 贵 5 倍，在业务上可能是净亏损——回到 [计算机视觉·第 7 章](/xiaoshus-blog/textbooks/ai/ai-core/computer-vision/07/) 的"部署权衡"视角。

**手段一：抢占式/现货实例（spot/preemptible）**。以被随时驱逐（典型给 30 秒–2 分钟通知）为代价，换取约 60–90% 的折扣。配套条件：(a) **检查点（checkpoint）频繁落盘**（[深度学习·第 8 章](/xiaoshus-blog/textbooks/ai/ai-core/deep-learning/08/) 的断点续训直接复用）；(b) 训练框架支持从最近 checkpoint 恢复；(c) 批量推理/训练优先用 spot，在线服务慎用。

**手段二：缓存**。相同/相似请求不重复计算：结果缓存（请求哈希 → 响应）、特征缓存（在线特征商店天然承担）、以及第 5 章将展开的 LLM 前缀缓存。缓存命中率 $h$ 下的平均延迟：

$$
E[T] = h \cdot t_{\text{cache}} + (1 - h) \cdot t_{\text{model}}, \qquad h = \frac{N_{\text{hit}}}{N_{\text{hit}} + N_{\text{miss}}}
$$

**手段三：容量分级**。批处理任务填谷（夜间跑满空闲容量）、在线服务保峰、开发调试用共享小实例；存储按访问频率分层（热数据 SSD，冷数据归档）。

## 4.7 隐私合规与安全

### 4.7.1 GDPR 思想与"删除权"难题

GDPR（欧盟《通用数据保护条例》，2018 生效）确立了数据最小化、目的限定、**被遗忘权/删除权（right to erasure, 第 17 条）**等原则。前两条落在数据管道上（[数据工程·第 4 章](/xiaoshus-blog/textbooks/ai/engineering/data-engineering/04/) 的数据治理可直接对接），而删除权撞上了 ML 的墙：**用户的数据不仅存在于表中，还被"揉"进了模型权重里**。选项从重到轻：

1. **机械重训**：过滤掉该用户数据后从头重训。正确但昂贵；配合"定期重训周期"（如每季度）可把删除延迟约束在可接受范围。
2. **机器遗忘（machine unlearning）**：结构性支持删除。代表方案 SISA（Sharded, Isolated, Sliced, Aggregated；Bourtoule et al., IEEE S&P 2021）：把数据切成多个分片独立训练子模型，聚合出最终模型；删除某用户只需重训其所在分片。用训练成本换取删除成本。
3. **影响函数估算**：估算删除某样本对参数的影响并做一阶修正——快，但只是近似，合规上是否充分仍存争议。

另一个常被低估的风险：模型可能**记忆（memorize）**训练数据中的敏感信息， Carlini 等人的记忆提取研究表明大模型可被诱导复述训练样本。缓解：训练前脱敏/去标识（注意：去标识 ≠ 匿名，重识别风险仍在）、差分隐私训练、对生成输出做过滤。

### 4.7.2 三类攻防概览

| 攻击 | 机制 | 典型文献 | 防御 |
|---|---|---|---|
| **模型窃取（model stealing）** | 通过公开预测 API 海量查询，拟合出功能等价的替代模型 | Tramèr et al., USENIX Security 2016 | 限流/鉴权、输出加噪或降精度、只返回 top-1、异常查询监控 |
| **数据投毒（data poisoning）/后门** | 污染训练数据，植入触发模式（backdoor）：输入带特定贴片即输出指定类 | Gu et al., "BadNets", 2017 | 数据来源审计与血缘（本节课主线!）、异常样本检测、投毒鲁棒训练 |
| **提示注入（prompt injection）** | 在用户输入或**模型读取的外部内容**（网页/文档/邮件）中夹带指令，劫持 LLM 行为；后者即"间接提示注入" | Greshake et al., 2023 | 权限分离（LLM 不持有敏感操作权限）、指令与数据通道隔离、输出护栏（第 5 章） |

三者的共同根源：**模型信任了它不该信任的输入/数据**。防御的组织学解法是把"数据从哪来"做成可审计的流水线属性——这又回到了本章的主题：一切安全实践最终都落在平台能力上。

## 4.8 关键公式速查

| 公式 | 含义与适用条件 |
|---|---|
| $c_{\text{req}} = C_{\text{总}}/\text{吞吐}$ | 单请求摊销成本；评估模型大小/精度的业务判据 |
| $E[T] = h\,t_{\text{cache}} + (1-h)\,t_{\text{model}}$ | 缓存命中率 $h$ 下的平均延迟；$t_{\text{cache}} \ll t_{\text{model}}$ |
| $c_{\text{spot,eff}} = c_{\text{spot}} / \big(1 - p \cdot f_{\text{lost}}\big)$ | spot 有效时价：$p$ 为每小时被驱逐概率，$f_{\text{lost}}$ 为每次驱逐平均损失的已完成工作比例（依赖 checkpoint 间隔） |
| 折扣盈亏：$\dfrac{c_{\text{od}}}{c_{\text{spot,eff}}} > 1$ | spot 划算当且仅当有效折扣超过损失；checkpoint 越密 $f_{\text{lost}}$ 越小 |
| 血统四元组 $(\text{数据版本},\ \text{代码版本},\ \text{超参/环境},\ \text{工件哈希})$ | 可复现性的充分信息集；注册表每条记录必须可还原 |

## 4.9 示例与案例

### 案例 1（手算）：spot 实例的成本期望

按需价 $c_{\text{od}} = 3.0$ 美元/卡时；spot 折扣 70%，即 $c_{\text{spot}} = 0.9$。被驱逐概率 $p = 0.1$ 次/卡时，每次驱逐平均损失 15 分钟已完成训练（checkpoint 每 30 分钟一次，平均损失半个间隔）。

1. 每卡时被驱逐损失的工作比例：$p \cdot f_{\text{lost}} = 0.1 \times 0.25 = 0.025$，即每计费 1 小时平均只有 0.975 小时是有效训练；
2. spot 有效时价：$c_{\text{spot,eff}} = 0.9 / 0.975 \approx 0.923$ 美元/有效卡时；
3. 相对按需价的实际节省：$1 - 0.923/3.0 \approx 69.2\%$（名义折扣 70%，实际到手 69.2%——损失很小）；
4. 敏感性：若把 checkpoint 间隔拉长到 2 小时（$f_{\text{lost}} = 1.0$），$c_{\text{spot,eff}} = 0.9/0.9 = 1.0$，节省降到 66.7%；若驱逐率升到 0.5 次/卡时（竞拍型市场常见），$c_{\text{spot,eff}} = 0.9/0.875 \approx 1.03$，节省 65.7%。**结论：决定 spot 划算程度的是驱逐率 × checkpoint 间隔的乘积，而不是折扣百分比本身。**

### 案例 2（代码）：从零实现一个最小模型注册表

不依赖任何平台，用约 60 行 Python 实现注册表的本质：**哈希工件 + 校验门禁 + 状态机**。

```python
# ch4_model_registry.py
# 依赖: 仅标准库 (hashlib, json, pathlib, datetime)
import hashlib
import json
from datetime import datetime
from pathlib import Path

class ModelRegistry:
    """最小模型注册表: 注册(哈希) -> 门禁校验 -> 晋升/回滚。"""

    STAGES = ["candidate", "staging", "production", "archived"]
    # production 的门禁: 评估指标必须超过这些下限, 且必须先经过 staging
    GATE = {"min_auc": 0.85, "must_pass_staging": True}

    def __init__(self, path="registry.json"):
        self.path = Path(path)
        self.db = json.loads(self.path.read_text()) if self.path.exists() \
            else {"models": {}}

    def _save(self):
        self.path.write_text(json.dumps(self.db, indent=2, ensure_ascii=False))

    def register(self, name, artifact_path, data_version, git_commit, metrics):
        """注册新版本: 记录血统四元组 + 工件哈希。"""
        h = hashlib.sha256(Path(artifact_path).read_bytes()).hexdigest()[:16]
        vid = f"v{len(self.db['models'].get(name, [])) + 1}"
        rec = {"version": vid, "sha256": h, "data_version": data_version,
               "git_commit": git_commit, "metrics": metrics,
               "stage": "candidate",
               "registered_at": datetime.now().isoformat(timespec="seconds")}
        self.db["models"].setdefault(name, []).append(rec)
        self._save()
        return vid, h

    def promote(self, name, vid, new_stage):
        """状态机迁移, 含门禁校验。返回是否成功。"""
        rec = next(m for m in self.db["models"][name] if m["version"] == vid)
        cur, nxt = self.STAGES.index(rec["stage"]), self.STAGES.index(new_stage)
        assert nxt == cur + 1, f"非法跳跃: {rec['stage']} -> {new_stage}"
        if new_stage == "staging" and rec["metrics"]["auc"] < self.GATE["min_auc"]:
            print(f"[GATE][拒绝] {name}/{vid} auc={rec['metrics']['auc']}"
                  f" < {self.GATE['min_auc']}")
            return False
        if new_stage == "production":
            prod = [m for m in self.db["models"][name]
                    if m["stage"] == "production"]
            if prod:                                   # challenger 必须 ≥ champion
                champ = max(prod, key=lambda m: m["metrics"]["auc"])
                if rec["metrics"]["auc"] < champ["metrics"]["auc"]:
                    print(f"[GATE][拒绝] {name}/{vid} auc={rec['metrics']['auc']}"
                          f" 不敌现任 {champ['version']}={champ['metrics']['auc']}")
                    return False
        rec["stage"] = new_stage
        self._save()
        print(f"[OK] {name}/{vid} -> {new_stage}")
        return True

    def current_production(self, name):
        """线上应加载的版本 (部署侧按此取模型, 回滚=切回旧版本)。"""
        prod = [m for m in self.db["models"][name] if m["stage"] == "production"]
        return max(prod, key=lambda m: m["registered_at"]) if prod else None

# ---- 演示一场完整的"注册 -> 拒绝 -> 再战 -> 上线 -> 回滚" ----
Path("model_v1.bin").write_bytes(b"\x00" * 1024)      # 假装是模型工件
Path("model_v2.bin").write_bytes(b"\x01" * 1024)
reg = ModelRegistry("registry.json")
reg.db = {"models": {}}                                # 演示从空表开始

reg.register("risk-model", "model_v1.bin", "data#2024-06-01",
             "a1b2c3d", {"auc": 0.88})
reg.register("risk-model", "model_v2.bin", "data#2024-06-15",
             "e4f5a6b", {"auc": 0.835})                # v2 指标不达标
reg.promote("risk-model", "v1", "staging")             # OK
reg.promote("risk-model", "v1", "production")          # OK
reg.promote("risk-model", "v2", "staging")             # [GATE][拒绝] 0.835<0.85
# 预期输出:
# [OK] risk-model/v1 -> staging
# [OK] risk-model/v1 -> production
# [GATE][拒绝] risk-model/v2 auc=0.835 < 0.85
print("production =", reg.current_production("risk-model")["version"])
# 预期输出: production = v1
```

## 4.10 常见误区与陷阱

1. **指标提升 = 模型更好的唯一判据**。忽略行为测试与数据校验，会放过"评估集过拟合"与"荒谬行为"；上线后监控（第 3 章）才是真相。
2. **注册表只当网盘用**。只存文件不记血统、不做门禁，注册表退化为目录——回滚时不知道旧版本是哪份数据训练的，可复现性归零。
3. **编排任务不幂等**。重试导致数据重复写入、指标重复统计；任何"先删后写"之外的副作用都要设计幂等键。
4. **只看折扣不看驱逐**（见案例 1 的敏感性分析）以及**开发/实验环境用按需全价卡**——成本的 80% 往往来自没人审计的笔记本训练与僵尸端点。
5. **把合规当法务部门的事**。删除权、数据最小化直接决定训练架构（SISA 分片、定期重训周期、数据血缘），架构定型后再补合规通常是推倒重来。

## 4.14 课后思考与练习

1. **概念**：为什么说"实验是 ML 流水线的一等公民"？如果只追踪代码 commit 不追踪数据版本，会丢失哪些归因能力？
2. **概念**：CheckList 的三类行为测试（MFT/INV/DIR）各设计两个针对"中文情感分析模型"的具体用例。
3. **计算**：GPU 按需价 2.5 美元/卡时，spot 折扣 60%，驱逐率 0.2 次/卡时，checkpoint 间隔 1 小时。求 spot 有效时价与实际节省。（校验值：$2.5 \times 0.4 = 1.0$；$1.0/(1-0.2\times0.5)=1.111$；节省约 55.6%。）
4. **计算**：某服务每秒 2000 请求，单请求摊销成本 0.0001 美元。若引入命中率 40% 的结果缓存（缓存命中成本按 1/10 估算），每小时总成本与平均延迟各降多少（设 $t_{\text{model}} = 20$ ms，$t_{\text{cache}} = 2$ ms）？（校验值：平均延迟 $20 \to 12.8$ ms，降幅 36%。）
5. **计算**：SISA 把数据切成 8 片独立训练。用户请求删除时需重训几个分片？相对整体重训的算力比是多少？（校验值：1 片；1/8。）
6. **编程**：扩展 4.9 案例 2 的注册表：加一个 `rollback()` 方法（把 production 指回上一版本），并为 `promote` 补充"archived 状态不可再晋升"的规则；为全部路径写 pytest 用例。
7. **编程**：用 Airflow（或其本地模拟器）写一条 5 节点 DAG：拉数据 → schema 校验（失败即终止）→ 训练 → 指标门禁 → 注册；故意让第 2 步失败，验证后续节点不被执行且告警被触发。
8. **编程**：实现 CheckList 式不变性测试器：对一个文本分类模型，自动生成 50 组同义替换对（用同义词典），断言预测一致率 ≥ 90%，并输出失败样例清单。
