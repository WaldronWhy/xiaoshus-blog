# 第 2 章 模型服务化

> **本章定位**：第 1 章把模型"出厂"，本章把它"上岗"：用稳定、可演进的网络接口把模型暴露给其他系统，并让它在并发流量下满足延迟承诺。前置要求：第 1 章（ONNX 与推理延迟）、[Python·第 7 章](/xiaoshus-blog/textbooks/ai/programming/python/07/)（模块化与测试）、《实验设计与评估》（A/B 检验的功效分析）。本章的部署形态与压测方法将被第 3 章的监控与第 5 章的 LLM 服务直接复用。

## 2.1 服务化架构模式：在线/批量/流式推理

"把模型变成服务"至少有三种截然不同的架构模式，选择错了后面全部返工：

| 模式 | 触发方式 | 延迟预算 | 典型例子 | 成本特征 |
|---|---|---|---|---|
| **在线推理**（online / real-time） | 用户请求同步触发 | 毫秒~几百毫秒 | 搜索排序、风控打分、机器翻译 | 必须为峰值流量保有容量，最贵 |
| **批量推理**（batch / offline） | 定时调度（如每小时/每晚） | 分钟~小时 | 全量用户次日推荐候选、报表特征打分 | 平峰填谷，可用 spot 资源，最便宜 |
| **流式推理**（streaming） | 事件到达即处理 | 秒级，逐条/微批 | Kafka 上的实时欺诈检测、IoT 异常告警 | 介于两者，需应对流量突刺 |

决策的第一问：**这个预测结果允许"多旧"？** 风控必须逐笔实时（在线）；"给每个用户算一份晨间推荐"完全可以是夜间批任务；中间态则是流式。大量 ML 系统的省钱秘诀就是把在线需求降级为批量需求——例如把"实时计算用户画像"改为"每小时刷新画像 + 实时叠加最近事件"。

另一个贯穿本章的模式是**同步 vs 异步**：在线推理通常是同步 RPC（客户端等结果）；批量任务常用异步 API（提交作业 → 返回 job id → 轮询/回调取结果）。异步模式天然解耦了流量与容量，是低成本处理突发的大杀器。

## 2.2 REST 与 gRPC 的技术权衡

模型服务的第一版接口几乎都从 REST（HTTP/1.1 + JSON）开始，但它不是唯一选项。

| 维度 | REST (HTTP/1.1 + JSON) | gRPC (HTTP/2 + Protobuf) |
|---|---|---|
| 序列化 | 文本 JSON，人类可读，体积大、解析慢 | 二进制 protobuf，需 `.proto` 契约，紧凑高效 |
| 接口契约 | 靠 OpenAPI 规范"事后描述" | `.proto` 文件"先于实现"定义，类型强校验 |
| 传输效率 | 连接复用有限（HTTP/1.1 队头阻塞） | HTTP/2 多路复用，单连接并发多请求 |
| 流式 | SSE / chunked（受限） | 原生支持服务端/客户端/双向流（LLM token 流式输出见第 5 章） |
| 生态调试 | curl/浏览器/网关直接可用 | 需要专用客户端或 grpcurl |
| 超时传播 | 各自为政 | deadline 随调用链自动传播 |

经验法则：**面向外部的 API 用 REST**（调试友好、网关/CDN 生态成熟）；**内部微服务之间、或高吞吐低延迟的点对点调用用 gRPC**（序列化省的毫秒在大 QPS 下收益显著）；两者并存也完全正常——外面 REST 网关，里面 gRPC。

无论哪种，都必须定义：请求/响应的 JSON Schema 或 proto、错误码语义（4xx 客户端错/5xx 服务端错/429 限流）、超时与重试策略（**重试必须考虑幂等性**，且要加指数退避——你在 [数据工程](/xiaoshus-blog/textbooks/ai/engineering/data-engineering/00/) 爬虫一节已经见过同样的礼貌原则）。

## 2.3 模型服务器：TorchServe 与 Triton 的架构与特性

自己用 Flask 包一层模型是学习项目；生产系统应使用**模型服务器（model server）**——一个专门为"加载模型 + 承接并发推理流量"设计的常驻进程。看两个代表：

**TorchServe**（PyTorch 官方）：

- 模型打包为 `.mar` 归档（权重 + 序列化图 + `handler` 代码 + 依赖清单）；
- **handler** 是一个约定接口的 Python 类，串联 `preprocess → inference → postprocess`，官方预置图像分类、文本分类等默认 handler；
- 分离**推理 API**（默认 8080）与**管理 API**（8081）：后者负责运行时注册/卸载/扩缩模型实例，即"不停服换模型"；
- 内建请求批处理（`batch_size`、`max_batch_delay`）与指标输出。

**NVIDIA Triton Inference Server**（部署侧事实标准之一）：

- **模型仓库（model repository）**是核心概念：一个约定目录结构 + 每模型 `config.pbtxt` 配置，支持版本目录 `1/ 2/ 3/`，天然承载多版本；
- **多 backend**：同一服务器可同时服务 TensorRT、ONNX Runtime、PyTorch、Python（任意自定义逻辑）模型——异构模型栈的统一入口；
- **dynamic batching**：服务器在毫秒级时间窗内把并发到达的单条请求拼成 batch（`max_batch_size` + `max_queue_delay_microseconds`），用 GPU 擅长的大 batch 换吞吐，代价是窗口期等待延迟；
- **instance_group**：每个模型可配置多个并发执行实例，实例数是调吞吐的核心旋钮；
- **ensemble/BLS**：把"前处理模型 → 主模型 → 后处理模型"声明式地连成流水线，由服务器内部调度；
- 原生输出 Prometheus 指标（推理计数、队列时长、GPU 利用率），与第 3 章的监控无缝衔接。

两者的共同启示：**模型服务器把"并发管理、批处理、版本管理、指标"这些横切关注点从你的业务代码中剥离**。自研推理服务只在有特殊需求（如重度业务逻辑耦合）时才值得。

## 2.4 dynamic batching 与并发模型

### 2.4.1 为什么批处理能换吞吐

在 [深度学习·第 8 章](/xiaoshus-blog/textbooks/ai/ai-core/deep-learning/08/) 你已经知道：GPU 的强项是一次算一批。batch=1 时 GPU 利用率可能不到 10%，batch=32 时吞吐可提升一个量级，而单条延迟只增加很小。**dynamic batching** 就是把"训练时的大 batch"搬到服务端：请求到达后先排队，攒满一个 batch 或超时即发车。设批处理窗口为 $\Delta$，一条请求的额外延迟在 $[0, \Delta]$ 上近似均匀分布，均值 $\Delta/2$——吞吐的货币是延迟，汇率由你配置。

### 2.4.2 Python 服务的并发模型

推理是 CPU/GPU 密集计算，这里有一个必须理解的现实：**CPython 的 GIL（全局解释器锁）使多线程无法并行执行 Python 字节码**。因此：

- 纯 Python 的预处理逻辑是瓶颈时 → 用**多进程**（uvicorn/gunicorn 的 `--workers`，每个 worker 独立加载模型）；
- 预处理主要是 NumPy/ONNX Runtime 这类 **C 扩展**（执行时会释放 GIL）→ 多线程/asyncio 也能并行；
- GPU 推理 → 每张 GPU 上若干执行实例（Triton 的 `instance_group`），实例内再用 CUDA stream 排队。

**每 worker 加载一份模型副本**是常被忽视的内存账：8 worker × 2 GB 模型 = 16 GB，部署前必须算清楚——这也是第 1 章"减小模型体积"在服务侧的直接回报。

## 2.5 延迟与吞吐的权衡：Little's Law

**Little's Law**（排队论中少有的普适定律）：

$$
L = \lambda \cdot W
$$

其中 $L$ 是系统内平均请求数（在途请求，含排队中与处理中），$\lambda$ 是平均到达率（QPS），$W$ 是请求在系统中的平均停留时间（排队 + 处理）。它对任何处于稳态的系统成立，与分布、调度策略无关——正如 [概率统计·第 5 章](/xiaoshus-blog/textbooks/ai/math-foundations/probability-statistics/05/) 强调的，有些结论强到不依赖分布假设。

**用途一：容量规划（正向算）**。承诺 1000 QPS、单请求端到端 50 ms，则系统内平均同时有 $L = 1000 \times 0.05 = 50$ 个请求在途。若每个 worker 串行处理（一次 1 个），需要至少 50 个并发槽位——这就是"并发数 = 流量 × 延迟"的规划公式。

**用途二：解释延迟爆炸（反向算）**。最简单的 M/M/1 模型（泊松到达 + 指数服务时长 + 单队列）给出请求平均停留时间：

$$
W = \frac{1}{\mu - \lambda} = \frac{1/\mu}{1 - \rho}, \qquad \rho = \frac{\lambda}{\mu}
$$

其中 $\mu$ 是服务率、$\rho$ 是利用率。注意 $1/(1-\rho)$ 这一项：利用率 50% 时延迟是纯服务时间的 2 倍，80% 时 5 倍，95% 时 **20 倍**——**延迟随负载非线性爆炸**。这就是为什么生产 SRE 的铁律是把稳态利用率控制在 70–80% 以下，也是为什么"压测通过 = 上线安全"是幻觉：压测的峰值之上没有余量。多服务器（$c$ 个并行槽位）时 $\rho = \lambda/(c\mu)$，形状类似：越接近 1 越陡。

还要区分两个延迟视角：**均值延迟**好看但会骗人（一条 10 秒的慢请求被 99 条 10 ms 摊平），**p99 延迟**才代表用户体验下界。批处理、垃圾回收、网络抖动都主要伤害尾部——本节实验（2.9）会让你亲手看到 p99 随利用率爆炸。

## 2.6 灰度发布、A/B 测试上线与回滚策略

新模型版本上线是本课最危险的瞬间：离线评估再好也可能在线翻车。标准的低风险路径：

1. **影子部署（shadow / dark launch）**：新版本接收真实流量的**镜像副本**，计算结果但只记录不返回。零风险观察延迟分布与异常率，代价是双倍算力。
2. **灰度/金丝雀发布（canary release）**：把 X% 真实流量切给新版本（1% → 5% → 25% → 100%），每档停留并检查**门控指标（guardrail metrics）**：错误率、p99 延迟必须不劣化；业务指标不允许显著下降。流量切分用路由表实现（网关按 user_id 哈希分桶，保证同一用户始终看到同一版本——否则 A/B 数据被污染）。
3. **A/B 实验门控**：灰度本身就是一次在线 A/B 实验。新旧版本的对比要按《实验设计与评估》的规范做：预先设定主要指标与最小可检测效应（MDE）、按功效分析确定最小灰度流量与时长、用假设检验判定显著性——**没算功效就宣布"新模型更好"是自欺**。
4. **回滚（rollback）**：上线不是成功才结束，而是"随时可以回头"。要求：(a) 旧版本模型**保持温热**（不卸载，或镜像仍在节点上）；(b) 回滚 = 路由表切回，分钟级完成，不触发重新部署；(c) 明确"什么信号触发自动回滚"（如错误率 > 1% 持续 5 分钟）与"谁有权按哪个按钮"。回滚要像消防演习一样**演练**过，而不是第一次执行就在故障夜。

与第 4 章的关系：这里的路由与门控是"发布流水线"的运行时部分；模型从哪来（版本从哪查）、谁能批准晋升到 production，是第 4 章模型注册表的职责。

## 2.7 完整示例：FastAPI 封装 sklearn 模型服务 + Dockerfile

下面是一个生产形态（最小版）的模型服务：启动时加载模型、带健康检查、带模型版本元数据、同时提供单条与批量预测端点。

```python
# app.py —— FastAPI 模型服务
# 依赖: pip install fastapi uvicorn scikit-learn joblib numpy
import os
from pathlib import Path

import joblib
import numpy as np
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

MODEL_PATH = Path(os.environ.get("MODEL_PATH", "model.joblib"))
MODEL_VERSION = os.environ.get("MODEL_VERSION", "v0")

# ---- 启动时加载模型一次 (而不是每次请求都加载) ----
if not MODEL_PATH.exists():
    # 首次运行时训练并落盘一个演示模型 (鸢尾花三分类)
    from sklearn.datasets import load_iris
    from sklearn.linear_model import LogisticRegression
    X, y = load_iris(return_X_y=True)
    model = LogisticRegression(max_iter=1000).fit(X, y)
    joblib.dump({"model": model, "sk_version": "demo"}, MODEL_PATH)

bundle = joblib.load(MODEL_PATH)
model = bundle["model"]

app = FastAPI(title="iris-classifier", version=MODEL_VERSION)

class PredictIn(BaseModel):
    # 四个特征, 严格类型与范围校验: 服务的第一道防线
    sepal_length: float = Field(ge=0, le=10)
    sepal_width:  float = Field(ge=0, le=10)
    petal_length: float = Field(ge=0, le=10)
    petal_width:  float = Field(ge=0, le=10)

    def to_vector(self) -> list[float]:
        return [self.sepal_length, self.sepal_width,
                self.petal_length, self.petal_width]

class PredictOut(BaseModel):
    label: int
    label_name: str
    probs: list[float]

@app.get("/health")           # 存活探针: 只检查进程活着
def health():
    return {"status": "ok", "model_version": MODEL_VERSION}

@app.get("/ready")            # 就绪探针: 检查模型真的可用
def ready():
    ok = model is not None
    return {"ready": ok, "model_version": MODEL_VERSION} if ok \
        else ({"ready": False}, 503)

@app.post("/predict", response_model=PredictOut)
def predict(item: PredictIn):
    X = np.array([item.to_vector()], dtype=np.float64)
    label = int(model.predict(X)[0])
    probs = model.predict_proba(X)[0].tolist()
    return PredictOut(label=label,
                      label_name=model.classes_[label],
                      probs=[round(p, 4) for p in probs])

@app.post("/predict_batch", response_model=list[PredictOut])
def predict_batch(items: list[PredictIn]):
    if not 1 <= len(items) <= 256:            # 批量上限: 保护服务器
        raise HTTPException(400, "batch size must be in [1, 256]")
    X = np.array([i.to_vector() for i in items], dtype=np.float64)
    labels = model.predict(X)
    probas = model.predict_proba(X)
    return [PredictOut(label=int(l), label_name=model.classes_[int(l)],
                       probs=[round(p, 4) for p in pr])
            for l, pr in zip(labels, probas)]

# 运行: uvicorn app:app --host 0.0.0.0 --port 8000 --workers 2
# 测试: curl -X POST localhost:8000/predict -H "Content-Type: application/json" \
#        -d '{"sepal_length":5.1,"sepal_width":3.5,"petal_length":1.4,"petal_width":0.2}'
# 预期响应: {"label":0,"label_name":"setosa","probs":[0.97,0.02,0.01]}  (近似)
```

## 2.8 关键公式速查

| 公式 | 含义与适用条件 |
|---|---|
| $L = \lambda W$ | Little's Law：稳态系统在途请求数 = 到达率 × 平均停留时间；分布无关 |
| $\rho = \lambda / (c\mu)$ | 利用率：$c$ 个并行服务槽位；稳态要求 $\rho < 1$ |
| $W = \dfrac{1/\mu}{1-\rho}$ | M/M/1 平均停留时间；$c=1$、泊松到达、指数服务时长 |
| $E[\text{批处理额外延迟}] = \Delta/2$ | 批处理窗口 $\Delta$ 内均匀发车假设下的均值额外延迟 |
| 并发槽数 $\ge \lambda \times W_{\text{SLO}}$ | 容量规划：由 SLO 延迟反推所需并发；实际按 $\rho \le 0.7$–$0.8$ 留余量 |

## 2.9 示例与案例

### 案例 1（手算）：容量规划

某风控模型服务，峰值流量 400 QPS，承诺 p99 ≤ 200 ms，实测单请求处理时间 40 ms（含排队前）。

1. 用 Little's Law 估在途请求：$L = 400 \times 0.04 = 16$（按纯服务时间）；
2. 每 worker 串行、单请求 40 ms → 单 worker 吞吐 $= 1/0.04 = 25$ QPS；裸容量需 $400/25 = 16$ 个 worker；
3. 按 $\rho \le 0.75$ 留余量：$16 / 0.75 \approx 21.3$，取 **22 个 worker**；
4. 验证利用率：$\rho = 400/(22 \times 25) = 0.727$，M/M/1 近似下平均停留 $W = 0.04/(1-0.727) \approx 0.147$ s，仍在 200 ms SLO 内（注意这是均值近似，p99 还需压测确认——手算只能定规模，不能定承诺）。

### 案例 2（代码）：从零模拟 M/M/1 队列，亲眼看延迟爆炸

用事件驱动模拟一个单队列服务，改变利用率 $\rho$，观察平均延迟与 p99。

```python
# ch2_mm1_simulation.py
# 依赖: numpy (标准库 heapq)
import heapq
import numpy as np

rng = np.random.default_rng(42)

def simulate_mm1(mu, lam, n=20_000):
    """事件驱动的 M/M/1 模拟: 泊松到达 + 指数服务 + FIFO 单服务器。
    mu: 服务率(1/秒), lam: 到达率(1/秒)。返回平均停留时间与 p99。"""
    assert lam < mu, "稳态要求 lam < mu"
    # 事件堆: (时间, 序号, 类型), 类型: a=到达
    t = 0.0
    events = []
    for i in range(n):
        t += rng.exponential(1 / lam)          # 到达间隔 ~ Exp(lam)
        heapq.heappush(events, (t, i))
    busy_until = 0.0                            # 服务器忙到何时
    waits, dones = [], []
    while events:
        t_arr, i = heapq.heappop(events)
        start = max(t_arr, busy_until)          # 空闲则立刻服务, 否则排队
        dur = rng.exponential(1 / mu)
        busy_until = start + dur
        waits.append(busy_until - t_arr)        # 停留 = 完成时刻 - 到达时刻
    waits = np.array(waits) * 1000              # 转 ms
    return waits.mean(), np.percentile(waits, 99)

mu = 100.0                                        # 每秒服务 100 个请求 (10ms/个)
for rho in (0.5, 0.8, 0.9, 0.95):
    lam = rho * mu
    mean_w, p99 = simulate_mm1(mu, lam)
    theory = 1 / (mu - lam) * 1000                # 理论平均停留 W = 1/(mu-lam)
    print(f"rho={rho:4.2f}  mean={mean_w:7.1f} ms (理论 {theory:6.1f})  "
          f"p99={p99:8.1f} ms")
# 预期输出 (固定种子, 数值可复现, 均值 ±10%、p99 ±25% 抽样波动):
# rho=0.50  mean=   20.7 ms (理论   20.0)  p99=     85.3 ms
# rho=0.80  mean=   51.4 ms (理论   50.0)  p99=    219.5 ms
# rho=0.90  mean=  103.8 ms (理论  100.0)  p99=    462.7 ms
# rho=0.95  mean=  208.9 ms (理论  200.0)  p99=    933.6 ms

# 这正是 2.5 节"利用率红线"与"盯尾部不看均值"的数值证据。
```

## 2.10 常见误区与陷阱

1. **在请求处理函数里加载模型**。每次请求反序列化一次模型，延迟增加数百毫秒；模型必须在应用启动时加载一次（对照 2.7 节写法）。
2. **只用均值监控延迟**。批处理窗口、GC、连接池抖动都藏进尾部；SLO 必须定义在 p95/p99 上，容量规划也应以尾部为约束。
3. **压测只测单接口的裸推理**。真实链路含鉴权、序列化、网络排队；压测要打完整端点，并覆盖"突发流量"场景（如 10 秒内从 0 拉到峰值），而不是只看平稳速率。
4. **灰度没有用户粘性**。按请求随机分流会让同一用户在不同版本间横跳，A/B 数据互相污染、体验不一致；应按用户/会话哈希分桶。
5. **回滚只写在文档里**。旧版本模型文件被新部署覆盖、路由表没人会改、负责人不在线——回滚能力必须通过真实演练验证（见综合项目三）。

## 2.13 进阶方向

1. **多阶段流水线服务**：检索 → 粗排 → 精排的级联推理架构（推荐系统标准形态），每阶段的延迟预算分配是一个独立的优化问题。
2. **自适应批处理**：批处理窗口随流量动态调整（流量低时缩窗保延迟，高峰时扩窗保吞吐），可从简单的斜率控制策略入手实现。
3. **Kubernetes 上的自动扩缩容**：基于 QPS 或自定义指标（如队列长度）的 HPA 扩缩容，结合第 4 章的成本工程理解"缩容到零"。
4. **服务网格与全链路压测**：Istio 类服务网格的金丝雀路由能力，与生产环境全链路影子流量压测。
