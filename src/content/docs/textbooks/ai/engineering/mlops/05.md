# 第 5 章 大模型时代的部署专题

> **本章定位**：LLM 把前四章的多条规则改写了：显存被 KV 缓存而不是权重吃掉、延迟要按 token 流式度量、批处理要在 token 粒度调度。本章是全课程的收官章，直接衔接 [自然语言处理·第 7 章](/xiaoshus-blog/textbooks/ai/ai-core/nlp/07/)（解码与 KV 缓存机制）。前置要求：第 1–4 章全部、[深度学习·第 5 章](/xiaoshus-blog/textbooks/ai/ai-core/deep-learning/05/)（自注意力）。

## 5.0 本章学习目标

学完本章，你能够：

1. 推导 KV 缓存的显存占用公式，计算给定模型/上下文/并发下的显存需求，并指出"显存墙"由权重与 KV 缓存两部分构成；
2. 解释 PagedAttention 的分页机制（逻辑块、块表、写时复制）以及它如何把缓存浪费从 60–80% 压到 4% 以下；
3. 说明连续批处理（continuous batching）与静态批处理的本质区别，并用模拟实验量化两者的吞吐差距；
4. 在 FP16 / GGUF Q4 / AWQ 之间为一个部署场景做量化选型，说清质量-显存-速度的三角取舍；
5. 用前缀缓存、语义缓存与 RAG 控制 LLM 服务的 token 成本；
6. 为一个 Agent 应用设计可观测性方案（逐跳 trace、token 记账、预算熔断），并把 LLM 评估线上化（在线评测 + 护栏）。

## 5.1 LLM 服务的独特挑战

在 [自然语言处理·第 7 章](/xiaoshus-blog/textbooks/ai/ai-core/nlp/07/) 你已经见过自回归解码的机制；站在部署视角，它带来三个结构性挑战。

**挑战一：两阶段计算画像完全不同**。一次生成 = 一次 **prefill**（对整个 prompt 并行计算，算术强度高，是**计算受限**的）+ $n$ 步 **decode**（每步只生成 1 个 token，但要读全部权重与全部 KV 缓存，是**带宽受限**的）。第 1 章的量化加速原理（省带宽）主要作用于 decode 阶段；prefill 阶段则更吃算力。两阶段的延迟通常分开报告：**TTFT**（time to first token，首 token 延迟，由 prefill 决定）与 **TPOT/ITL**（每输出 token 时间/相邻 token 间隔，由 decode 决定）。

**挑战二：显存墙（memory wall）**。显存由两块构成：权重（静态）+ KV 缓存（随上下文线性增长）。KV 缓存每 token 字节数：

$$
M_{\text{KV/token}} = 2 \times L \times H_{\text{kv}} \times d_{\text{head}} \times b \quad (\text{K 与 V 各一份，故乘 2})
$$

其中 $L$ 为层数、$H_{\text{kv}}$ 为 KV 头数（GQA/MQA 下远小于注意力头数）、$d_{\text{head}}$ 为每头维度、$b$ 为每元素字节数。以 Llama-2-7B（$L=32$，$H_{\text{kv}}=32$，$d_{\text{head}}=128$，FP16）为例：每 token $2 \times 32 \times 32 \times 128 \times 2 = 512\ \text{KB}$——**缓存 2048 token 的上下文就是 1 GB**，与权重同量级。并发 64 路长对话时 KV 缓存轻松吃掉上百 GB：**显存，而不是算力，决定了能同时服务多少路对话**。

**挑战三：长尾延迟与输出长度不可知**。输出长度由内容决定（可能是 5 个 token 也可能是 5000 个），无法预先分配资源；输出慢的请求长期占用 KV 缓存，与 [概率统计·第 5 章](/xiaoshus-blog/textbooks/ai/math-foundations/probability-statistics/05/) 中重尾分布的直觉一致——LLM 服务的延迟分布天然重尾，p99 与均值可能差一个量级。

## 5.2 LLM 推理引擎：vLLM 与 PagedAttention

### 5.2.1 旧方案的问题：按最大长度预留

朴素的 KV 缓存管理沿袭第 2 章的静态思维：给每个请求预留"最大上下文长度"的连续显存（如 2048 token × 0.5 MB）。vLLM 论文（Kwon et al., SOSP 2023）实测，这种方案导致 **60–80% 的 KV 缓存显存被浪费**：外部碎片（空闲块太小无法分配给新请求）+ 内部碎片（实际只用了 300 token 却占着 2048 的槽）+ 预留浪费（为不可能达到的最大长度买单）。浪费直接转化为"能并发服务的路数变少"——还记得第 2 章的 Little's Law 吗：并发路数 = 吞吐的硬上限。

### 5.2.2 PagedAttention：把操作系统的分页搬进显存

vLLM 的核心思想一字不差地借自虚拟内存：**把每个请求的 KV 缓存切成固定大小的块（block，典型 16 个 token），按需分配、不必连续**；一个**块表（block table）**记录"该请求的第 $i$ 个逻辑块 → 物理块号"的映射。注意力计算时按块表间接寻址。

三重收益：

1. **碎片趋近于零**：块按需分配，内部浪费最多 $15/16 \approx 94\%$ 降为平均不到半个块，论文实测整体浪费 **< 4%**（对比此前系统的 60–80%），等效于把并发路数提高一个量级；
2. **前缀共享（prefix sharing）**：多个请求共享同一系统提示词时，其 KV 块通过**引用计数 + 写时复制（copy-on-write）**共享——只有分叉处才复制新块。beam search 与并行采样同样受益；
3. **可换出（swapping）**：物理块可整体换出到 CPU 内存，长尾请求不再钉死显存。

效果（论文数据）：vLLM 相比 HuggingFace Transformers 原生推理吞吐提升最高 **24 倍**，相比 TGI 最高 **3.5 倍**（长输入场景）。

### 5.2.3 引擎速览

| 引擎 | 定位 | 关键特性 |
|---|---|---|
| **vLLM** | 高吞吐 GPU 服务 | PagedAttention、连续批处理、前缀缓存、OpenAI 兼容 API |
| **TGI**（HuggingFace） | GPU 服务 | 连续批处理、token 流式、丰富量化支持、与 HF 生态集成 |
| **llama.cpp** | CPU/边缘设备 | GGUF 格式、k-quant 量化、mmap 按需加载、无 GPU 也能跑 |

选型经验：GPU 上线选 vLLM 或 TGI（工程上差别在生态与运维偏好）；端侧/离线分析/无卡环境选 llama.cpp；三者都支持 OpenAI 风格 API，切换成本低——**接口标准化让引擎成为可替换件**（第 4 章"别造无差异重活"的又一例证）。

## 5.3 服务策略：token 流式、并发调度与连续批处理

**token 流式输出**：生成式请求的感知延迟由 TTFT 主导——等 8 秒出全文 vs 1 秒开始逐字吐出，用户体验天壤之别。工程实现用 SSE（HTTP 服务端推送事件）或 gRPC 服务端流，逐 token（或逐块）推送。由此监控也要换标尺：LLM 服务的核心 SLO 通常是 **TTFT p99** 与 **TPOT p99**，而不是"响应时间"（对照第 2 章 2.5 节：换了一个度量的对象，方法论不变）。

**连续批处理（continuous batching）**：第 2 章 dynamic batching 以**请求**为粒度攒批发车——批内最长的请求没结束，整个 batch 都不能动。对输出长度方差巨大的 LLM，这是灾难性的等待。Orca（OSDI 2022）提出**迭代级调度（iteration-level scheduling）**：每解码一步（一次前向）都重新编排 batch——某请求结束立即腾出槽位，排队请求立即插入。batch 成员在每个迭代层面都在变化，故称"连续"。这与第 2 章 2.9 节你亲手模拟过的"槽位及时复用"是同一个道理，只是粒度从请求细化到 token；5.9 案例 2 会把两种策略的差距算给你看。

**并发调度**的其他要点：prefill 与 decode 混批时会互相拖累（长 prompt 的 prefill 卡住别人的 decode 步），工程上有 chunked prefill（把 prefill 切片插入解码节拍）等折中；投机解码（speculative decoding，小模型起草 + 大模型并行验证）可在输出分布不变的前提下加速 decode 2–3 倍（Leviathan et al., 2023）。

一个值得记住的调度器心智模型（伪代码）：

```text
每个解码节拍:
    1. 收割: 输出 EOS 或达到上限的请求 → 释放其 KV 块, 返回结果
    2. 补位: 从等待队列取请求, prefill 其 prompt, 分配 KV 块
    3. 预算检查: 剩余 KV 显存不够时, 换出/抢占低优先级请求 (或拒绝新请求)
    4. 一步解码: 对当前 batch 内所有请求并行生成 1 个 token
```

所有主流引擎都是这个骨架的变体；它们的大部分工程差异集中在第 3 步（显存不足时的抢占与换出策略）——这正是 PagedAttention 把 KV 块做成可管理"页"的回报：**块可以被分配、共享、换出、重算，就像操作系统的页一样**。

## 5.4 量化部署实操：GGUF 与 4-bit 的取舍

第 1 章的量化理论直接落地，但 LLM 场景多了几个新维度。

**权重 4-bit（W4A16）**是当前 GPU 部署的主流甜点：权重存 4-bit，计算时反量化回 FP16 做矩阵乘（激活仍是 FP16）。代表方案：**GPTQ**（Frantar et al., ICLR 2023，基于逐层二阶信息最小化重构误差）与 **AWQ**（Lin et al., 2023，按激活分布保护"重要通道"）。收益：权重显存缩到 1/4（7B 模型 14 GB → 约 3.5–4 GB，单卡 24 GB 可跑 13B），decode 带宽压力同样缩到 1/4 → 吞吐约 2–3 倍。代价：4-bit 的量化误差在复杂推理任务上可测（约 1–3 个百分点的基准波动），且 GPTQ 需要校准数据。

**LLM.int8()**（Dettmers et al., NeurIPS 2022）揭示了 8-bit 量化的关键现象：Transformer 的激活存在极少数**异常特征维度（outlier features）**，幅值比常态大几十倍且集中在固定的维度；这些维度必须保持 FP16，其余 INT8，混合分解计算，才能无损。这一"按维度混合精度"的思想被后续所有 LLM 量化方案继承。

**GGUF 与 k-quant**（llama.cpp 生态）：Q4_K_M（约 4.8 bit/权重的混合精度 k-quant）是 CPU/端侧的常用档位，困惑度损失通常很小；Q8_0 几乎无损但只省一半显存。**选型速查**：

| 档位 | 显存/权重 | 质量 | 适用 |
|---|---|---|---|
| FP16 | 14 GB (7B) | 基准 | 质量敏感、显存充裕 |
| INT8 / Q8 | ~7 GB | 近乎无损 | 通用 GPU 服务 |
| Q4 / AWQ / GPTQ | ~4 GB | 略降，推理任务可测 | 显存紧张、高并发吞吐优先 |
| Q2/Q3 极端档 | ~2 GB | 明显退化 | 仅玩具/极端端侧，生产慎用 |

实操流程（GPU）：从 HuggingFace 下载 AWQ 权重 → `vllm serve`（或 TGI）→ 用固定测试集对比量化前后在目标任务上的表现（第 1 章 1.6 节的"数值一致性 + 压测"方法，把输出对比从精确等值放宽为评测分数）。实操流程（CPU/端侧）：把模型转换为 GGUF → 选 Q4_K_M 量化 → llama.cpp 加载并压测 tokens/s。

## 5.5 RAG 与缓存的成本优化

LLM 的"每次请求都要付全价"（token 计费 + 算力）让第 4 章的成本工程有了新的主战场。

**RAG（retrieval-augmented generation）**（Lewis et al., 2020）：把"知识"从参数里搬回外存——检索相关片段塞进上下文。部署视角的三笔账：(1) 检索延迟（向量库毫秒级）远小于重新生成；(2) prompt 变长 → prefill 变贵，要靠"只取 top-k 片段 + 片段去重"控制；(3) 知识更新 = 更新索引而不是重训模型——**这是把"持续训练"问题（第 3 章）降维成"数据管道"问题**。

**三层缓存**（自上而下命中率递减、收益递增）：

1. **前缀缓存（prefix/prompt caching）**：系统提示词、few-shot 示例、RAG 索引说明在多请求间不变——PagedAttention 的块共享让这部分 KV 只算一次。实现上 vLLM/TGI 均内建；
2. **语义缓存（semantic cache）**：把"北京今天天气"与"今天北京天气怎么样"识别为同一意图——以请求嵌入的相似度做 key。命中率 $h$ 的平均成本照抄第 4 章公式 $E[c] = h c_{\text{cache}} + (1-h) c_{\text{model}}$；注意**错命中会答非所问**，相似度阈值要保守；
3. **结果缓存**：确定性任务（结构化抽取、分类）按请求哈希精确缓存。

**成本记账单位换成了 token**：`c_req = (prompt_tokens × 单价 + completion_tokens × 单价 + 基础设施摊销)`。控制输出长度（"最多 N 个 token"硬约束 + 提示词要求精炼）通常是最便宜的省钱手段——输出 token 往往比输入贵数倍。

## 5.6 Agent 应用的部署与可观测性

在 [自然语言处理·第 7 章](/xiaoshus-blog/textbooks/ai/ai-core/nlp/07/) 你已了解 Agent 的"规划 → 工具调用 → 观察 → 再规划"循环。部署视角下，Agent = **一个请求展开为一张不确定深度的调用图**，这带来三件新事：

1. **逐跳可观测性（trace）**：每次 LLM 调用、每次工具调用都是带父子关系的 span，记录 token 数、延迟、成败与内容摘要（可用 Langfuse/LangSmith 类工具）。没有 trace 的 Agent 出错时你只能看到"最终答案错了"，无法定位是检索没取到、工具失败还是模型幻觉；
2. **token 预算与熔断**：Agent 的成本 = 各跳之和，且循环失控（模型反复尝试同一失败工具）会让成本无上限。工程底线：**最大步数、最大累计 token、单请求最大耗时**三个硬上限 + 超限熔断降级；
3. **工具延迟纳入 SLO**：Agent 的端到端延迟 = Σ(LLM 跳延迟) + Σ(工具延迟)，工具接口也要有超时与重试策略（第 2 章 2.2 节的契约设计在此兑现）。

一条真实的失败 trace 长什么样（节选）：

```text
req#8842  trace_id=7f3a
├─ llm.call#1 (plan)            in=1850 tok  out=120 tok  1.9s  ok
├─ tool.call#1 (search_orders)  latency=0.4s ok  hits=0        ← 检索为空
├─ llm.call#2 (retry plan)      in=1970 tok  out=120 tok  2.1s  ok
├─ tool.call#2 (search_orders)  latency=0.4s ok  hits=0        ← 同样为空
├─ llm.call#3 (retry plan)      in=2090 tok  out=120 tok  2.2s  ok   ← 已循环 2 次
└─ budget.gauge                 steps=6/12  tokens=6380/20000  elapsed=11s/30s
```

从这份 trace 里，"客服反馈答非所问"被定位到**工具返回空结果后模型转入自由发挥**（幻觉），而不是检索质量或模型能力问题——修复方式是给工具加"空结果必须如实告知并引导转人工"的指令与护栏，而非重新微调。**可观测性的价值不在看，而在能把故障归因到正确的跳。**

## 5.7 LLM 评估的线上化：在线评测与护栏

离线评测集（你熟悉的 MMLU 式基准）与线上表现之间存在鸿沟：用户的问题分布每天在变（回到第 3 章：分布漂移是常态）。线上化分两翼：

**在线评测（online evaluation）**：

- **用户反馈信号**：点赞/点踩、采纳率、会话时长——便宜但有偏（沉默的大多数）；
- **LLM-as-a-judge**：用强模型给对话质量打分或做两两对比（Zheng et al., 2023，MT-Bench/Chatbot Arena 的方法），可大规模自动评测新版本，但要警惕 judge 的位置偏好与自我偏好——**judge 本身也要抽样人工校验**（这是《实验设计与评估》的评估者信度问题换了个皮）；
- **影子对比**：第 2 章的 shadow 部署 + judge 打分 = 零风险的新版本评估流水线。

**护栏（guardrails）**：输入侧与输出侧的双向过滤——

- 输入侧：内容安全分类（拒绝违法/有害请求）、提示注入检测（第 4 章 4.7.2）、越狱（jailbreak）模式库；
- 输出侧：敏感内容过滤、**忠实性检查**（RAG 场景断言"答案中的每个事实都能在检索片段中找到支撑"——即幻觉检测）、格式校验（JSON schema）；
- 专用护栏模型（如 Meta 的 Llama Guard，Inan et al., 2023）把"判别这条输入/输出是否违规"本身做成一个可部署的小模型——**用 ML 监控 ML**（第 3 章三层监控里"模型层"的自我指涉版）。

```text
用户输入 ─▶ [输入护栏: 安全分类 / 注入检测] ─▶ 检索(RAG) ─▶ LLM 生成
                │ 拒绝(记录原因码)                              │
                ▼                                              ▼
            固定话术回复                          [输出护栏: 忠实性校验 / 敏感过滤 / 格式校验]
                                                               │ 拦截(记入第3章监控面板)
                                                               ▼
                                                    修复后的回复或降级话术 ─▶ 用户
```

护栏的每一道拦截都必须**记录原因码**并进入第 3 章的监控面板——护栏的误杀率本身就是需要盯住的核心指标。

## 5.8 关键公式速查

| 公式 | 含义与适用条件 |
|---|---|
| $M_{\text{KV/token}} = 2 L H_{\text{kv}} d_{\text{head}} b$ | 每 token KV 缓存字节数；GQA 下 $H_{\text{kv}} <$ 注意力头数 |
| $M_{\text{total}} = M_{\text{weights}} + N_{\text{并发}} \times \bar{s} \times M_{\text{KV/token}}$ | 显存容量规划：权重 + 并发路数 × 平均上下文长度 |
| TTFT / TPOT | 首 token 延迟（prefill 主导）/ 每 token 延迟（decode 主导）；LLM 服务的两个核心 SLO |
| 浪费率 $= 1 - \dfrac{\sum_i s_i}{T \times B}$ | 批处理槽位浪费率：$\sum s_i$ 为总解码步数，$T$ 为总步数，$B$ 为槽位数 |
| $E[c] = h c_{\text{cache}} + (1-h) c_{\text{model}}$ | 缓存命中率 $h$ 下的单请求期望成本（承第 4 章） |
| $c_{\text{req}} = p \cdot n_{\text{prompt}} + q \cdot n_{\text{completion}}$ | token 经济学：$p, q$ 为输入/输出单价，通常 $q > p$ |

## 5.9 示例与案例

### 案例 1（手算）：显存墙的构成

Llama-2-7B（$L=32$，注意力头 32，$d_{\text{head}}=128$，FP16）服务 64 路并发、平均上下文 2048 token：

1. 权重显存：$7\times10^9 \times 2\ \text{B} = 14$ GB；
2. 每 token KV：$2 \times 32 \times 32 \times 128 \times 2 = 524{,}288$ B $= 0.5$ MB；
3. KV 总量：$64 \times 2048 \times 0.5\ \text{MB} = 64$ GB；
4. 合计约 78 GB——**一张 80 GB 的 A100 刚好装满，且这是静态预留的理想值**（朴素实现还要为最大上下文 4096 预留，直接爆）。

改用 GQA 版架构（$H_{\text{kv}}=8$）：每 token $= 0.125$ MB，64 路 × 2048 = **16 GB**，缓解 4 倍。这个计算解释了两个行业事实：为什么新模型都用 GQA/MQA，为什么 KV 缓存管理（PagedAttention）是 LLM 服务的第一战场。

### 案例 2（代码）：静态批处理 vs 连续批处理的槽位模拟

模拟 10 个输出长度差异很大的请求、4 个解码槽位：静态批处理整批同进同出；连续批处理在 token 粒度补位。比较总步数与槽位浪费率。

```python
# ch5_static_vs_continuous.py
# 依赖: 仅标准库
L = [6, 12, 9, 33, 41, 18, 27, 5, 22, 15]      # 10 个请求的输出 token 数
B = 4                                           # 解码槽位数

# ---- 静态批处理: 每 B 个请求成批, 整批走 max 长度 ----
static_steps = sum(max(L[i:i+B]) for i in range(0, len(L), B))
work = sum(L)
static_waste = 1 - work / (static_steps * B)

# ---- 连续批处理: 每步 refill -> 全体解码一步 -> 移除完成者 ----
queue, active, steps, done = list(L), [], 0, 0
while done < len(L):
    steps += 1
    while queue and len(active) < B:            # 空槽立即补位 (token 粒度)
        active.append(queue.pop(0))
    active = [a - 1 for a in active]            # 每个活跃槽解码 1 个 token
    done += sum(1 for a in active if a == 0)    # 本步完成的请求
    active = [a for a in active if a > 0]
cont_waste = 1 - work / (steps * B)

print(f"总解码量 {work} token-步, 槽位数 {B}")
print(f"静态批处理: {static_steps} 步, 槽位浪费率 {static_waste:.1%}")
print(f"连续批处理: {steps} 步, 槽位浪费率 {cont_waste:.1%}")
print(f"吞吐提升约 {static_steps / steps:.2f}x")
# 预期输出 (确定性, 无随机因素):
# 总解码量 188 token-步, 槽位数 4
# 静态批处理: 96 步, 槽位浪费率 51.0%
# 连续批处理: 54 步, 槽位浪费率 14.5%
# 吞吐提升约 1.78x
# 判读: 静态策略的浪费来自"批内等待最长者"(如 [22,15] 一批空转 7 步) 与
#      "批间等待"(第 3 批只有 2 个请求也要等前两批全部结束); 连续策略
#      把浪费压到仅剩块尾。真实 LLM 负载的输出方差远大于本例,
#      vLLM 论文中端到端吞吐收益可达数倍到数十倍。
```

### 案例 3（代码）：KV 缓存显存计算器与容量规划

把 5.8 的公式写成一个计算器，用于部署前的容量预演（对照 [深度学习·第 8 章](/xiaoshus-blog/textbooks/ai/ai-core/deep-learning/08/) 的显存记账习惯）。

```python
# ch5_kv_memory_planner.py
# 依赖: 仅标准库
def kv_per_token_bytes(n_layers, n_kv_heads, head_dim, bytes_per_elem):
    """每 token 的 KV 缓存字节数: K 与 V 各一份。"""
    return 2 * n_layers * n_kv_heads * head_dim * bytes_per_elem

def plan_memory(model_name, n_params, n_layers, n_kv_heads, head_dim,
                bytes_per_elem, ctx_len, concurrency, reserve_gb=1.0):
    """显存容量规划: 权重 + KV 缓存 + 运行时预留。"""
    w_gb = n_params * bytes_per_elem / 1024**3
    kv = kv_per_token_bytes(n_layers, n_kv_heads, head_dim, bytes_per_elem)
    kv_gb = concurrency * ctx_len * kv / 1024**3
    total = w_gb + kv_gb + reserve_gb
    print(f"{model_name}: 权重 {w_gb:.1f} GB + KV {kv_gb:.1f} GB "
          f"(每 token {kv/1024:.0f} KB x {concurrency}路 x {ctx_len}tok) "
          f"+ 预留 {reserve_gb} GB = {total:.1f} GB")
    return total

# Llama-2-7B (MHA, 32 个 KV 头), FP16
plan_memory("L2-7B/MHA/fp16",  7e9, 32, 32, 128, 2, 2048, 64)
# Llama-3-8B (GQA, 8 个 KV 头), FP16 —— 架构相同量级, KV 省 4 倍
plan_memory("L3-8B/GQA/fp16",  8e9, 32,  8, 128, 2, 2048, 64)
# 同模型换 4-bit 权重 (激活/KV 仍按 fp16 计, 权重近似折算)
plan_memory("L3-8B/GQA/w4a16", 8e9, 32,  8, 128, 0.5, 2048, 64)
# 预期输出:
# L2-7B/MHA/fp16: 权重 13.0 GB + KV 64.0 GB (每 token 512 KB x 64路 x 2048tok) + 预留 1.0 GB = 78.0 GB
# L3-8B/GQA/fp16: 权重 14.9 GB + KV 16.0 GB (每 token 128 KB x 64路 x 2048tok) + 预留 1.0 GB = 31.9 GB
# L3-8B/GQA/w4a16: 权重 3.7 GB + KV 16.0 GB (每 token 128 KB x 64路 x 2048tok) + 预留 1.0 GB = 20.7 GB
# 判读: (1) MHA -> GQA 把 KV 从 64 GB 压到 16 GB, 一张 4090(24GB) 从"装不下"
#          变成"装得下但必须上 4-bit 权重"; (2) 低精度权重省的是静态项,
#          长上下文高并发时 KV 这一项才是主导 —— "显存墙"两层墙要分开拆。
```

扩展方向：把 PagedAttention 的块分配（块大小 16 token、写时复制）加进这个计算器，估算"共享系统提示词的前缀缓存在 100 路并发下省多少 KV"——你会得到一个与 5.5 节前缀缓存收益直接对应的数字。

## 5.10 常见误区与陷阱

1. **只给权重算显存**。14 GB 的 7B 模型 ≠ 14 GB 够用：KV 缓存常比权重大（案例 1）。显存规划必须写并发路数与上下文长度两个假设。
2. **用"平均响应时间"做 LLM SLO**。生成式请求的体验由 TTFT 与 TPOT 决定，全文平均时间掩盖了流式体验；SLO 必须按 token 粒度定义。
3. **把静态批处理的思想直接搬到 LLM**。"攒 32 个请求一起跑"在输出长度方差大的负载下会灾难性地互相等待；必须 token 级调度。
4. **语义缓存阈值设太松**。相似 ≠ 相同（"北京天气" vs "上海天气"嵌入距离可能很近）；语义缓存的错命中是静默错误，要按请求类型分级启用并保守设阈值。
5. **Agent 没有预算上限就上线**。循环失控的单请求能烧掉数千 token × 数十跳；没有熔断的 Agent 不该接生产流量。
6. **全信 LLM-as-a-judge**。judge 有系统性偏好（偏长答案、偏自己的风格）；只用 judge 不抽人工校验的在线评测，会把 judge 的偏见固化为产品方向。
