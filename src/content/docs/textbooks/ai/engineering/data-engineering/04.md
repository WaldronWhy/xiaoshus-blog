# 第 4 章 数据版本控制与数据质量体系

> **本章定位**：前两章解决"数据怎么处理"，本章解决"处理结果如何可信、可追溯、可持续"。内容涵盖 DVC 版本管理、数据卡片与数据治理、断言式质量校验（Great Expectations 思想）与标注一致性度量（Cohen's kappa）。本章为《模型部署与 MLOps》的数据监控与持续训练直接铺垫，也是《实验设计与评估》可复现性协议的数据侧支柱。

## 4.0 本章学习目标

- 能够解释"代码用 Git 管、数据用 DVC 管"的分工原理，并说出大数据不适合放 Git 的两个原因。
- 能够完成 DVC 的完整工作流：`init/add/push/checkout`、`.dvc` 元数据文件、`dvc.yaml` 流水线与 `dvc repro` 增量重算。
- 能够编写一份合格的数据卡片（data card），覆盖来源、采集过程、组成、用途与局限五个必备部分。
- 能够用 Great Expectations 的思想把质量六维度写成断言（expectation），并解释"校验结果文档化"在团队协作中的价值。
- 能够手算两人标注的 Cohen's kappa，并解释为什么"表面一致率 85%"可能一文不值。
- 能够设计一个标注质量管理流程：指南、试标、金标题、仲裁与一致性门槛。

## 4.1 为什么模型需要数据版本控制

回顾《Python 程序设计》第 7 章：Git 让代码的每一次变更可追溯、可回滚、可协作。但一个 ML 项目的产物是三元组（数据、代码、模型），三者共同决定实验结果：

$$\text{模型} = f(\text{代码},\ \text{数据},\ \text{配置}).$$

只给 $f$ 建版本库而让"数据"悬空，可复现性就是一句空话——"上季度那个 0.87 的模型是用哪版数据训的？"这个问题若答不上来，团队就在用不可信的结果做决策。更尖锐的三个理由：

1. **数据一直在变**：上游业务每天追加新记录、修正旧字段，"同一个数据集"两周后已经不是同一份数据（数据漂移，data drift）。
2. **模型无法解释问题时，只能回看数据**：指标回退的第一嫌疑人是数据变更而非代码变更，追溯起点是数据版本。
3. **合规与审计**：《个人信息保护法》、GDPR 与模型监管都要求"删某用户的数据后重新评估模型"成为可执行操作——前提是知道每版数据里有什么。

### 4.1.1 为什么 Git 不能直接管大数据

两个硬约束：Git 对象按内容全量存储且为性能要求文件常驻内存（数十 GB 的数据集会把 `git status` 拖到分钟级）；Git 针对文本 diff 优化，对二进制大文件每次变更都是全量副本。Git LFS 缓解了部分问题，但 DVC 的设计更贴合 ML 场景：**Git 只存指针（元数据），数据本体存到专用远程存储**（S3/GS/OSS/SSH/本地目录均可），二者通过内容哈希关联。

## 4.2 DVC 的完整使用

### 4.2.1 核心机制：内容寻址

DVC 对每个数据文件/目录计算内容哈希（默认 MD5），把"路径 → 哈希"写进 `.dvc` 元数据文件（提交给 Git），数据本体放进 `.dvc/cache/` 并推送到远程。任何一次数据变更 → 哈希变化 → `.dvc` 文件变化 → Git 提交记录了变更。检出旧版本代码时，`dvc checkout` 按 `.dvc` 里的哈希从缓存/远程取回对应数据本体。**数据版本 = Git 提交 + 内容哈希**，语义与代码版本完全对齐。

### 4.2.2 完整工作流（命令清单）

```bash
# 0) 一次性初始化(假设已有 git 仓库)
pip install dvc
dvc init
git commit -m "Initialize DVC"

# 1) 接入远程存储(课程项目可用本地目录模拟, 生产用 s3:// 或 oss://)
dvc remote add -d storage /path/to/shared/dvc-store
git add .dvc/config && git commit -m "Add DVC remote"

# 2) 把数据纳入版本管理: 数据本体被移入cache, 留下指针文件
dvc add data/raw/reviews.parquet
git add data/raw/reviews.parquet.dvc .gitignore   # dvc add 自动把本体加进 .gitignore
git commit -m "Add raw reviews dataset v1"

# 3) 数据更新后: 哈希变化, 提交新指针
#    (重新生成 data/raw/reviews.parquet 之后)
dvc add data/raw/reviews.parquet
git commit -m "Update raw reviews dataset: +50k rows, dedup applied"

# 4) 协作者检出某历史版本后取回对应数据
git checkout <old-commit>
dvc checkout        # 按旧 .dvc 指针从 cache/remote 拉回数据本体

# 5) 推送/拉取大文件本体到远程
dvc push            # 本体上传远程
dvc pull            # 新机器/新成员一键取回
```

### 4.2.3 流水线：`dvc.yaml` 与增量重算

DVC 的第二层价值是把"数据 → 特征 → 训练 → 评估"声明成依赖图（DAG），只重算受影响的阶段：

```yaml
# dvc.yaml
stages:
  clean:
    cmd: python src/clean.py
    deps: [data/raw/reviews.parquet, src/clean.py]   # 依赖: 输入数据与代码
    outs: [data/clean/reviews.parquet]               # 产出
    metrics: [reports/clean_metrics.json]            # 可 diff 的指标
  features:
    cmd: python src/features.py
    deps: [data/clean/reviews.parquet, src/features.py]
    outs: [data/feat/train.parquet, data/feat/test.parquet]
  train:
    cmd: python src/train.py
    deps: [data/feat/train.parquet, src/train.py, params.yaml]
    outs: [models/model.pkl]
    metrics: [reports/eval.json]
```

```bash
dvc repro            # 依 DAG 自底向上, 只重跑依赖有变化的阶段
dvc exp show         # 对比各次实验的 metrics (配合 params.yaml 的超参)
```

`dvc repro` 的增量逻辑与第 3 章 Spark 的血缘思想同源：都依赖"输入内容哈希 + 代码"判断产出是否失效。`params.yaml` 中的超参数变更只触发 `train` 阶段重跑——数据不动时特征与训练解耦，这正是《实验设计与评估》课程中"消融实验"的工程载体。

### 4.2.4 其他工程要点

- **实验对比**：`dvc exp run`/`dvc exp show` 把每次 `dvc repro` 的指标与参数快照成"实验卡片"，相当于给《实验设计与评估》的消融实验提供了免费记账本。
- **缓存治理**：`.dvc/cache` 会随版本累积，定期 `dvc gc`（配合 `--cloud` 同步清理远程）回收不再被任何提交引用的本体。
- **敏感数据**：`.gitignore` 挡住了数据本体进 Git，但 `.dvc` 指针与数据卡片仍可能含敏感描述——个人信息相关字段在数据卡片中只写口径不写样例值。

## 4.3 数据卡片与数据治理

### 4.3.1 Datasheets 与 Data Cards

数据本身需要"说明书"。Gebru 等（2018/2021）提出 **Datasheets for Datasets**：为每个数据集回答动机、组成、采集过程、预处理、分发与维护等结构化问题。Google 的 **Data Cards**（Pushkarna et al., 2022）将其推向产品化，强调面向下游使用者披露用途与风险。一份最小合格的数据卡片包含五部分：

1. **来源与采集**：数据从哪来？爬虫还是 API？采集时段？采样方式有无偏倚？
2. **组成与规模**：多少样本、多少字段、类别分布、已知缺失模式。
3. **预处理历史**：清洗规则、去重方法、标注指南版本——对应第 1 章清洗流程的固化文档。
4. **预期用途与非用途**：训练什么任务？明确列出不应使用的场景（如医学数据不得用于招聘决策）。
5. **局限与偏差**：已知的覆盖缺口（如中老年用户占比仅 5%）、标注一致性的量化结果（4.5 节的 kappa）。

### 4.3.2 数据治理的工程落点

治理 = 把上面的文档与流程变成制度：schema 变更需评审（数据契约，第 1 章进阶方向）、敏感字段登记与脱敏（个人信息保护）、数据卡片随每个数据版本提交（放 Git 仓库里与 `.dvc` 指针同目录）。这三件事的共同目的是让"这版数据能不能用"成为**可审计的问题**而非口头信任。

## 4.4 数据质量监控：断言式校验

### 4.4.1 Great Expectations 思想

数据测试的困境：写不出"正确答案"，只能写"合理约束"。Great Expectations（GE）把约束表达为**断言（expectation）**——对数据的可执行声明，如 `expect_column_values_to_not_be_null("user_id")`、`expect_column_values_to_be_between("age", 0, 120)`、`expect_column_pair_values_a_to_be_greater_than_b`。若干断言组成**校验套件（suite）**，对某个数据批次（batch）运行后生成结构化的**校验结果（validation result）**与人可读的**数据文档（Data Docs）**。

这与《Python 程序设计》第 7 章的单元测试（pytest 的断言）是同一思想在不同对象上的应用——**代码的单元测试测逻辑，数据的测试测分布**。四个设计要点：

1. **断言要分层**：硬断言（主键非空、schema 字段齐全——违反即流水线失败报警）与软断言（某列缺失率 < 5%——违反只记录趋势，观察是否恶化）。
2. **把第 1 章六维度映射为断言组**：完整性 → 非空率；唯一性 → 主键唯一；有效性 → 值域/正则；一致性 → 跨表引用完整；及时性 → 最新时间戳距今 < 24h；准确性 → 与抽样人工核对结果比对。
3. **对分布而非只对单值断言**：数值列的均值/分位数与历史窗口比较（可用第 5 章与《实验设计与评估》的假设检验）；类别列的新增取值报警——这是 drift 监控的雏形。
4. **结果必须文档化且可追溯**：每次校验绑定数据版本（DVC 哈希）与代码版本（Git 提交），出问题时能定位到"哪版数据、哪条断言、何时开始失败"。

第 1 章的六维度可以直接翻译成断言组，形成一张"质量体检单"：

| 质量维度 | 断言示例 | 失败动作 |
|---|---|---|
| 完整性 | `expect_column_values_to_not_be_null("user_id")` | 硬：阻断流水线 |
| 唯一性 | 主键唯一、无重复行 | 硬：阻断 |
| 有效性 | 值域 `[0,120]`、正则匹配邮箱格式 | 硬：阻断 |
| 一致性 | 子表外键均在主表、同一实体两处年龄相同 | 硬：阻断 |
| 及时性 | `max(event_time)` 距今 < 24h | 软：告警 |
| 准确性 | 与权威源抽样的偏差率 < 1%（离线跑） | 软：周报 |

### 4.4.2 指标漂移的量化：PSI

工程上常用总体稳定性指数（PSI, Population Stability Index）量化一个数值分布相对基线的偏移：把取值分箱后,

$$\mathrm{PSI} = \sum_{i=1}^{B}\left(p_i^{\text{new}} - p_i^{\text{base}}\right)\ln\frac{p_i^{\text{new}}}{p_i^{\text{base}}},$$

即逐箱计算新旧占比差的 KL 散度式加权和。经验阈值：$\mathrm{PSI} < 0.1$ 基本稳定；$0.1$–$0.25$ 需关注；$> 0.25$ 显著漂移，应触发排查。它是《模型部署与 MLOps》线上监控的入门级指标（更严格的分布检验，如 KS 检验、MMD，将在《实验设计与评估》与 MLOps 课程展开）。

## 4.5 数据标注管理与标注质量控制

### 4.5.1 为什么标注是质量链条的最后一环

监督学习的 $y$ 来自人工标注，标注错误的直接后果是《机器学习》第 1 章"偏差项"里不可消除的一部分——模型拟合的"真值"本身是错的。质量控制手段按顺序：**标注指南**（类目定义、边界案例裁决规则，随标注迭代而版本化）→ **试标校准**（全员标同一批样本，讨论分歧后修订指南）→ **金标题（golden set）**（混入已知答案的题目实时检验标注员水平）→ **多人独立标注 + 一致性度量** → **仲裁**（分歧样本交资深标注员或委员会裁决）。

### 4.5.2 Cohen's kappa：去掉"蒙对"的一致率

两名标注员对 $N$ 个样本独立标注，表面一致率 $p_o = (\text{一致数})/N$ 有个致命缺陷：类别极不平衡时，两人**都蒙多数类**也能得到很高的一致率。Cohen's kappa（1960）扣除随机一致：

$$\kappa = \frac{p_o - p_e}{1 - p_e},$$

其中 $p_e = \sum_k a_k b_k$ 是两人独立随机标注的期望一致率（$a_k, b_k$ 分别是两人在类别 $k$ 上的边际占比）。$\kappa = 1$ 完全一致；$\kappa = 0$ 等于随机；负数劣于随机。Landis 与 Koch（1977）的粗略分档：0.21–0.40 尚可，0.41–0.60 中等，0.61–0.80 充分，0.81–1.00 几乎完全一致——工程上，主观任务（情感极性、图像细粒度类别）通常要求 $\kappa \geq 0.7$ 才放行进入训练集。

### 4.5.3 手算与加权扩展

两人对 200 条评论标注"正面/负面"：A 标 120 正 / 80 负，B 标 110 正 / 90 负，一致 160 条（其中 100 条同为正）。$p_o = 160/200 = 0.8$；$p_e = 0.6\times 0.55 + 0.4 \times 0.45 = 0.33 + 0.18 = 0.51$；$\kappa = (0.8 - 0.51)/0.49 \approx 0.59$。**校验值：$\kappa \approx 0.592$，按 Landis-Koch 属"中等"**——表面 80% 的一致率在扣除运气后缩水到 59%，这就是不平衡类别下必须用 kappa 的原因。有序类别（如"差/中/良/优"）应改用加权 kappa（Weighted Cohen's kappa，把"差标成良"与"差标成优"计不同的惩罚）；多标注员场景可用 Fleiss' kappa 或 Krippendorff's alpha。

## 4.6 关键公式速查

| 公式 | 含义 | 适用条件 |
|---|---|---|
| $\kappa = (p_o - p_e)/(1 - p_e)$，$p_e = \sum_k a_k b_k$ | 两标注员一致性（扣随机一致） | 两名标注员、名义类别；有序类别用加权版 |
| $\mathrm{PSI} = \sum_i (p_i^{new} - p_i^{base})\ln\frac{p_i^{new}}{p_i^{base}}$ | 分布漂移量化 | 需先分箱；$p_i^{base}$ 为 0 的箱需平滑处理 |
| 模型 $= f(\text{代码},\ \text{数据},\ \text{配置})$ | 可复现性的三元组 | 三者都要版本化，缺一不可 |
| DVC 版本 $=$ Git 提交（指针） $+$ 内容哈希（本体） | 数据版本控制语义 | 本体存远程存储，指针进 Git |

## 4.7 示例与案例

### 案例 1（手算）：kappa 计算已在 4.5.3 给出。再做一次带"蒙对风险"的对照：若类别为 95% 负 / 5% 正，两人都乱标但偏向负类，$p_o$ 可达约 0.9 而 $p_e \approx 0.9$，$\kappa \approx 0$——表面完美，实际毫无一致性信息。请自行取数验证。（提示：$a = (0.97, 0.03)$，$b = (0.97, 0.03)$ 时 $p_e = 0.9409 + 0.0009 = 0.9418$。）

### 案例 1b（手算）：PSI 的一个完整计算

基线分布把某数值列分 3 箱，占比 $p^{\text{base}} = (0.5, 0.3, 0.2)$；新批次占比 $p^{\text{new}} = (0.42, 0.33, 0.25)$。

$$\mathrm{PSI} = (0.42-0.5)\ln\frac{0.42}{0.5} + (0.33-0.3)\ln\frac{0.33}{0.3} + (0.25-0.2)\ln\frac{0.25}{0.2}$$
$$= (-0.08)(-0.1744) + (0.03)(0.0953) + (0.05)(0.2231) = 0.0140 + 0.0029 + 0.0112 \approx 0.028.$$

**校验值：PSI ≈ 0.028 < 0.1，分布基本稳定。** 若新占比变为 $(0.2, 0.3, 0.5)$（首末箱对调），请自行重算——结果应远超 0.25，触发排查。（注意 PSI 各项恒非负——它是对称 KL（Jeffreys 散度）的一种形式，这也是它优于"只看均值差"的原因。）

### 案例 2（代码）：断言式质量校验的最小实现 + kappa 计算

```python
# ch4_quality_checks.py
# 依赖: numpy, pandas (GE 思想的最小自实现, 生产请用 great_expectations 库)
import numpy as np
import pandas as pd

rng = np.random.default_rng(3)
n = 2000
df = pd.DataFrame({
    "user_id": rng.integers(1, 3000, n),                     # 故意含重复
    "age": rng.integers(10, 90, n),
    "amount": np.round(rng.lognormal(3, 1, n), 2),
    "event_time": pd.date_range(end=pd.Timestamp.now().floor("s"),
                                periods=n, freq="min"),      # 最近两天的分钟级数据
})
df.loc[rng.choice(n, 50, replace=False), "age"] = np.nan       # 注入缺失
df.loc[df.index[:5], "age"] = 150                              # 注入无效值

# ---------- 断言(Expectation)思想的最小实现: 每条返回 (是否通过, 明细) ----------
def assert_not_null(df, col, min_rate=0.99):
    rate = df[col].notna().mean()
    return rate >= min_rate, {"null_rate": round(float(1 - rate), 3)}

def assert_between(df, col, lo, hi, min_rate=0.999):
    ok = df[col].dropna().between(lo, hi)
    rate = ok.mean() if df[col].notna().any() else 1.0
    return rate >= min_rate, {"violations": int((~ok).sum())}

def assert_unique(df, col):
    return bool(df[col].is_unique), {"duplicates": int(df[col].duplicated().sum())}

def assert_fresh(df, col, max_lag_hours=24):
    lag = pd.Timestamp.now() - df[col].max()
    return lag <= pd.Timedelta(hours=max_lag_hours), {"lag": str(lag).split(".")[0]}

suite = {   # 硬断言(失败即阻断流水线) vs 软断言(失败先记录、观察趋势)
    "user_id 唯一(硬)":  assert_unique(df, "user_id"),
    "age 缺失率<1%(软)": assert_not_null(df, "age"),
    "age∈[0,120](硬)":   assert_between(df, "age", 0, 120),
    "amount>0(硬)":      (bool((df["amount"] > 0).all()), {}),
    "时效<24h(软)":      assert_fresh(df, "event_time"),
}
for name, (ok, detail) in suite.items():
    print(f"[{'PASS' if ok else 'FAIL'}] {name}  {detail}")
# 预期输出:
# [FAIL] user_id 唯一(硬)  {'duplicates': 531}
# [FAIL] age 缺失率<1%(软)  {'null_rate': 0.025}
# [FAIL] age∈[0,120](硬)   {'violations': 5}
# [PASS] amount>0(硬)  {}
# [PASS] 时效<24h(软)  {'lag': '0 days 00:00:00'}

# ---------- Cohen's kappa ----------
def cohens_kappa(a, b):
    a, b = pd.Series(a), pd.Series(b)
    cats = sorted(set(a) | set(b))
    po = (a == b).mean()
    ae = a.value_counts(normalize=True)
    be = b.value_counts(normalize=True)
    pe = sum(ae.get(k, 0) * be.get(k, 0) for k in cats)
    return (po - pe) / (1 - pe)

labels_a = rng.choice([0, 1], 200, p=[0.6, 0.4])
flip = rng.random(200) > 0.85                 # B 以 15% 概率给出不同标注
labels_b = np.where(flip, 1 - labels_a, labels_a)
k = cohens_kappa(labels_a, labels_b)
print(f"表面一致率 = {(labels_a == labels_b).mean():.3f}, kappa = {k:.3f}")
# 预期输出: 表面一致率 = 0.820, kappa = 0.627   (0.61~0.80, "充分"档下缘)
```

## 4.8 常见误区与陷阱

1. **只版本化代码不版本化数据**。实验记录里写"用了 3 月数据"毫无意义——3 月的哪个快照？质量断言对应哪版？复现失败的第一原因。
2. **把 `dvc add` 用在会频繁变化的大文件上却不 push**。本地 cache 丢失 = 数据版本永久丢失。远程存储是 DVC 工作流的必要组成部分，不是可选项。
3. **质量断言只写软断言**。全部断言都"记录但不拦截"，等于没有质量体系。必须明确哪些断言失败会阻断流水线（硬断言）并触发告警。
4. **用表面一致率管理标注团队**。类别不平衡时 90% 的一致率可能意味着 kappa ≈ 0。质量门槛必须建立在扣除随机一致后的指标上。
5. **数据卡片写成"一次性文档"**。数据更新后卡片不同步，比没有卡片更危险——它给出过时的信任。把卡片更新挂进 `dvc repro` 的 review 流程。

## 4.11 进阶方向

- **数据契约（data contract）的自动化执行**：schema + 质量断言 + SLA 打包为上下游接口协议，在 CI 中强制校验；需要补充 schema registry（如 Protobuf/Avro）与事件驱动架构知识。
- **标注质量的高级度量**：多标注员的贝叶斯真值推断模型（Dawid-Skene 模型：同时估计每人的混淆矩阵与真值先验）；需要补充 EM 算法（《机器学习》第 5 章）。
- **ML 元数据与血缘追踪**：DVC 之上的 MLflow、LakeFS 与 OpenLineage，把"数据→特征→模型→评估"全链路血缘入湖；需要补充元数据图模型知识。
- **面向大模型的评测污染检测**：训练语料与基准测试集的 n-gram/嵌入重叠审计；衔接第 5 章去重技术。
