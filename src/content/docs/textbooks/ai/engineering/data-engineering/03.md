# 第 3 章 大规模数据处理：从单机到集群

> **本章定位**：数据从"兆字节"长到"太字节"时会发生什么。本章先分析单机为何先于模型崩溃（内存与 IO 瓶颈），再对比数据格式（CSV/Parquet/JSONL）与单机大数据工具（分块、DuckDB、Polars），最后建立 MapReduce→Spark 的分布式范式与湖仓架构、流处理概念。它是第 4 章流水线规模化与综合项目基准测试的理论基础。

## 3.0 本章学习目标

- 能够用存储层级模型解释"为什么 100 GB 的数据在 32 GB 内存的机器上不只是一慢，而是会崩溃"，并估算给定任务的内存需求。
- 能够从列存/行存、压缩、谓词下推三个角度解释 Parquet 快于 CSV 的原因，并用基准实验验证。
- 能够用 pandas 分块、DuckDB、Polars 三种技术处理超出内存的数据集，并说出三者的取舍。
- 能够手写 word count 的 MapReduce 伪代码，解释 RDD 的懒执行、血缘（lineage）与宽窄依赖。
- 能够区分数据湖、数据仓库与湖仓一体三种架构的 schema 策略与适用场景。
- 能够解释 Kafka 的发布-订阅模型与三种时间窗口（滚动/滑动/会话）的语义。

## 3.1 为什么单机会先于模型崩溃

### 3.1.1 一笔内存账

机器内存是有限且昂贵的，存储层级（storage hierarchy）从寄存器→L1/L2/L3 缓存→内存→SSD→HDD，容量递增、速度递减，量级大致为：L3 缓存几十 MB（纳秒级）、内存几十 GB（百纳秒级）、SSD 数 TB（微秒级）、HDD 数 TB（毫秒级）。

pandas 的默认模式是**全内存物化**：`pd.read_csv` 把整个文件解析为对象图后，内存占用通常是文件大小的 2–6 倍（原因：每行每列的 Python 对象开销、64 位数值类型、字符串对象头）。于是一笔简单的账：32 GB 内存的机器，读一个 8 GB 的 CSV 就可能触发操作系统级危机——不是"慢"，而是**崩溃**：

- 物理内存耗尽 → 操作系统开始把内存页换出到磁盘（swap）→ 每次访问都多付一次毫秒级代价 → 程序慢百倍；
- swap 也耗尽 → OOM killer 直接终止进程，几小时的处理前功尽弃。

而模型训练所需的显存往往比这更小（GBDT 在百万样本上几百 MB 就够）。所以**数据处理先于建模崩溃**：模型的胃口在后面，数据的胃口在前面先撑爆机器。

### 3.1.2 IO 瓶颈：顺序与随机的鸿沟

《数据结构与算法》第 1 章用复杂度数数 CPU 指令，IO 世界需要同样的尺子，单位从"次比较"换成"字节搬运"：

$$T_{\text{read}} \approx \frac{\text{数据量}}{\text{有效带宽}}.$$

关键事实：HDD 顺序读约 100–200 MB/s，随机读只有每秒 100–200 次 IOPS（每次都要机械寻道）；SSD 顺序读数 GB/s，随机 IOPS 数万到数十万。**顺序与随机可以差三个数量级**——这就是为什么"能不能顺序扫一遍"决定了系统设计：

- 扫一遍 100 GB @ SSD 1 GB/s ≈ 100 秒，可行；随机访问 100 GB 的千万次小读 @ 0.1 ms/次 ≈ 17 分钟起步。
- 列存格式（3.2 节）的本质就是"只顺序读需要的列"；排序与聚簇的本质是"把随机访问变成顺序扫描"。

内存装不下 + 必须多遍扫描 = 需要外存算法（external memory algorithms）；单机外存也扛不住吞吐 = 需要横向扩展到集群。这是本章后半部分的逻辑起点。

### 3.1.3 处置策略的阶梯

把上面的分析收敛成一张决策阶梯（按代价递增），后续 3.2–3.4 节逐级展开：

1. **减量**：列裁剪、`dtype` 降位（int64→int32/float32、category 类型）、行过滤——先把"需要处理的字节数"压到最小，往往一步就解决问题。
2. **分块/懒执行**：生成器式逐块（pandas chunksize）或查询计划优化后只取所需（DuckDB/Polars），内存占用与总数据量解耦。
3. **外核（out-of-core）**：让引擎管理磁盘溢写（DuckDB 自动、Spark 本地模式同理），接受数量级的减速但保证正确完成。
4. **横向扩展**：把计算搬到数据旁边（数据本地性），用多机并行换墙钟时间，支付的是分布式复杂度。

纪律只有一条：**每一级都先做 3.1.1 的那笔账**，用数字判断当前级是否真的不够，再决定升级。

## 3.2 数据格式对比：CSV、JSONL 与 Parquet

### 3.2.1 三种格式的本质差异

- **CSV**：行存纯文本，人类可读，无类型（一切靠解析器猜），无压缩，无 schema。每列都要读、解析慢、体积大。
- **JSONL**：行存文本，每行一个 JSON 对象。半结构化（每行可有不同字段——日志场景的刚需），但冗余更大（字段名每行重复）。
- **Parquet**：**列存**二进制格式。三个决定性优势：
  1. **只读需要的列**：分析查询常用 10 列中的 2 列，列存直接跳过其他 8 列的 IO；
  2. **列内同型数据压缩率高**：同类值相邻，RLE/字典编码/压缩算法效果远超行存，文件常缩小到 CSV 的 1/5–1/10；
  3. **谓词下推与统计信息**：Parquet 的行组（row group）带 min/max 统计，`WHERE dt > '2024-01-01'` 可以整组跳过（谓词下推，predicate pushdown）。
  另外列存把 schema 写进文件——"写入即定形"，与 CSV 的 schema-on-read 相对。

深入一层看压缩为什么在列上这么有效。列内数据同型且往往高度冗余，编码器按序应用三类手段：**字典编码**（把重复字符串替换成小整数，`category` 列 4 个取值 → 每行 2 bit）→ **游程编码（RLE）**（连续相同值只存"值 × 重复次数"，排好序的列上收益巨大）→ **通用压缩**（zstd/snappy 吃掉剩余规律）。这就是为什么"先排序再写 Parquet"是免费的性能优化：排序让同类值聚集，RLE 与 min/max 裁剪同时受益。

### 3.2.2 类型与 schema 的坑

- **CSV 的类型推断**：解析器逐列"猜"类型，经典事故包括：区号 `0102` 被读成整数丢了前导零、混合列（`"N/A"` 与数字混排）被整体推断为字符串、日期被读成 `2024.06` 浮点。工程规则：读 CSV 时**显式传 dtype 与日期格式**，或干脆在读入后立即校验 schema。
- **Parquet 的 schema 演化**：写 schema 进文件意味着加列/改类型需要版本管理策略（Delta/Iceberg 提供 schema evolution 支持，见 3.5 节）。下游消费方要能容忍"新增列"，但要拒绝"改语义不改名"——那是数据契约问题（第 4 章）。

### 3.2.2 基准实验：同一份数据，三种命运

```python
# ch3_format_benchmark.py
# 依赖: numpy, pandas, pyarrow, duckdb, 时间测量用 time
import time
import numpy as np
import pandas as pd

rng = np.random.default_rng(0)
n = 5_000_000
df = pd.DataFrame({
    "user_id": rng.integers(0, 500_000, n),
    "amount": rng.lognormal(3, 1, n).round(2),
    "category": rng.choice(["food", "travel", "tech", "other"], n),
    "ts": pd.date_range("2024-01-01", periods=n, freq="s"),
})

def bench(fn, *args, **kw):
    t0 = time.perf_counter(); out = fn(*args, **kw)
    return time.perf_counter() - t0, out

t_w, _ = bench(df.to_csv, "bench.csv", index=False)          # 写 CSV
t_c, _ = bench(df.to_parquet, "bench.parquet")               # 写 Parquet
t_r_csv, df2 = bench(pd.read_csv, "bench.csv", parse_dates=["ts"])
t_r_par, df3 = bench(pd.read_parquet, "bench.parquet")
q1 = lambda d: d.loc[d["category"] == "travel", "amount"].mean()
t_sel_csv, _ = bench(q1, df2)                                # 内存中过滤
import duckdb
t_duck, out = bench(lambda: duckdb.sql(
    "SELECT avg(amount) FROM 'bench.parquet' WHERE category='travel'").fetchall())
import os
print(f"文件大小:   CSV {os.path.getsize('bench.csv')/1e6:.0f} MB, "
      f"Parquet {os.path.getsize('bench.parquet')/1e6:.0f} MB")
print(f"写: CSV {t_w:.1f}s, Parquet {t_c:.1f}s")
print(f"全量读: CSV {t_r_csv:.1f}s, Parquet {t_r_par:.1f}s")
print(f"内存过滤: pandas {t_sel_csv:.2f}s")
print(f"DuckDB 直查 Parquet(含谓词下推): {t_duck:.2f}s, 结果={out[0][0]:.2f}")
# 参考输出（一台普通笔记本 SSD 上的实测值；绝对值因机器而异，量级与比值稳定）:
# 文件大小:   CSV 196 MB, Parquet 69 MB          <- 体积约为 1/3
# 写: CSV 8.2s, Parquet 1.0s                     <- 差 8 倍
# 全量读: CSV 3.1s, Parquet 0.3s                 <- 差 10 倍
# 内存过滤: pandas 0.16s
# DuckDB 直查 Parquet(含谓词下推): 0.01s, 结果=33.08
#   <- 比先全量物化再过滤快 16 倍: 只解压 1 列 + 行组裁剪 + 多线程
```

实验结论（请在你的机器上复现并填写自己的数字）：Parquet 体积约为 CSV 的 1/4–1/3，读写快数倍；DuckDB 对 Parquet 的聚合查询甚至快于"pandas 先全量物化再过滤"，因为它只解压需要的列并跳过不满足谓词的行组。**分析型负载选 Parquet 是默认答案，CSV 只留给人类交互的边界。**

## 3.3 单机大数据技术

### 3.3.1 pandas 分块（chunking）

`pd.read_csv(..., chunksize=1_000_000)` 返回迭代器（回忆《Python 程序设计》第 3 章生成器——分块读取正是生成器的生产级应用）。内存里永远只有一个块；对**可分解聚合**（sum/count/max）逐块累积，对排序、全局去重这类需要全量信息的操作不适用（需外归并或哈希分桶）。近似统计则可用《数据结构与算法》第 7 章的流式算法：蓄水池采样取得代表子样本、Count-Min Sketch 估计重尾频次、HyperLogLog 数基数。

### 3.3.2 DuckDB：进程内分析型 SQL 引擎

DuckDB 是嵌入式的 OLAP 数据库（类比"分析场景的 SQLite"）：列式执行、向量化、多线程、可直接查询 Parquet/CSV 文件而**无需导入**，也支持与 pandas/Arrow 对象零拷贝互操作。当你的数据装不进内存又不想搭集群时，DuckDB 是默认首选。它还能实现"out-of-core"执行：内存不够时自动把中间结果溢写到磁盘。

```python
# 分块与 DuckDB 的等价处理：计算每类金额总和
import pandas as pd, duckdb

total_chunk, total_duck = 0.0, None
for chunk in pd.read_csv("bench.csv", chunksize=1_000_000):   # 内存安全
    total_chunk += chunk.groupby("category")["amount"].sum()

total_duck = duckdb.sql("SELECT category, sum(amount) FROM 'bench.csv' GROUP BY 1").df()
# 校验: 两者按 category 对齐后 sum 差值应 < 1e-3 (浮点求和顺序不同的微小误差)
```

### 3.3.3 Polars 概览

Polars 是基于 Rust 与 Apache Arrow 内存格式的新一代 DataFrame 库：表达式 API + **懒执行**（先构建查询计划，优化器做谓词下推/投影裁剪后再执行）+ 多线程并行。`polars.scan_csv(...).filter(...).group_by(...).collect()` 的懒模式会自动只读所需列。它与 DuckDB 的分工：Polars 提供 DataFrame 编程体验（替代/补充 pandas），DuckDB 提供 SQL 接口与存储引擎，两者都基于 Arrow 生态互通。

**单机技术选型小结**：数据 < 内存 → pandas 足矣；装不下但单文件可放磁盘 → DuckDB/Polars 懒执行；需要全量重排序/复杂图算法且单机外存也慢 → 分布式（3.4 节）。

| 维度 | pandas 分块 | DuckDB | Polars（lazy） |
|---|---|---|---|
| 编程接口 | DataFrame 迭代 | SQL | DataFrame 表达式 |
| 执行模型 | 单线程逐块 | 向量化多线程、可溢写磁盘 | 多线程 + 查询计划优化 |
| 直接查文件 | 否（需逐块读） | 是（CSV/Parquet 免导入） | 是（scan_* 懒扫描） |
| 全局排序/去重 | 困难（需外存归并） | 内建 | 内建 |
| 适用者 | 已有 pandas 代码的小改动 | SQL 熟手、分析查询 | 追求性能的数据管道 |

## 3.4 分布式计算范式：MapReduce → Spark

### 3.4.1 MapReduce：把"单机算法"升级为"集群分治"

Dean 与 Ghemawat（2004）提出的 MapReduce 把计算拆成两个用户定义函数：`map(k, v) → [(k2, v2)]` 与 `reduce(k2, [v2]) → result`，框架负责分布式执行、容错与那个最昂贵的环节——**shuffle**：按 key 把 map 输出重新分区、跨节点传输、排序后喂给 reduce。word count 是它的"hello world"：

```
map(line):        for w in line.split(): emit(w, 1)
reduce(word, [1,1,...]): emit(word, sum([1,1,...]))
```

为什么这样设计就能扩展？因为它把计算约束成**无共享（shared-nothing）的两阶段数据流**：map 阶段各节点独立处理本地数据分片（embarrassingly parallel），只有 shuffle 一个同步点。代价也来自 shuffle：跨节点网络传输与落盘使 MapReduce 在多步迭代任务（如 PageRank、机器学习训练）中把中间结果写满 HDFS，性能低下。

### 3.4.2 Spark：RDD、懒执行与宽窄依赖

Zaharia 等人（2012）提出 RDD（Resilient Distributed Dataset，弹性分布式数据集）：不可变的分布式记录集合，核心创新是**血缘（lineage）**——记录"我是由哪些转换从哪些数据得来"，节点故障时凭血缘重算丢失分区，而无需昂贵的多副本数据。

两个关键机制：

- **懒执行（lazy evaluation）**：`map/filter` 等转换（transformation）只记入执行计划不立即执行，遇到动作（action，如 `collect/count/save`）才触发。优化器因此能看到全局计划做优化（如把 filter 推到 join 之前）。对比 Polars 的懒执行——同一思想在不同层的再现。
- **宽窄依赖（narrow vs wide dependency）**：窄依赖（map、filter）中每个父分区最多喂一个子分区，可流水线执行无需网络传输；宽依赖（groupByKey、join、repartition）需要 shuffle。Spark 在窄依赖间做流水线优化，把 shuffle 最小化——**写 Spark 代码的第一性能法则就是减少宽依赖/少 shuffle**（例如 `reduceByKey` 优于 `groupByKey().map(...)`，前者在 map 端先做局部聚合）。

word count 的 Spark 版：

```python
# 概念代码(PySpark 语法, 无需在单机运行)
# lines = sc.textFile("hdfs://logs/2024/*.log")
# counts = (lines.flatMap(lambda l: l.split())
#                .map(lambda w: (w, 1))
#                .reduceByKey(lambda a, b: a + b))   # 窄依赖链 + 一次宽依赖
# counts.saveAsTextFile("out/")                      # action 触发执行
```

### 3.4.3 什么时候才真的需要集群

工程判断：单机 DuckDB/Polars 可以处理到 TB 级的**扫描式分析**；需要集群的信号是——数据增量快于单盘吞吐、多步 shuffle 密集型作业耗时不可接受、需要多用户并发查询同一份数据、需要容错的长时间作业。**先穷尽单机，再上分布式**：分布式把开发、调试、运维复杂度提高一个数量级。

### 3.4.4 shuffle 成本的一笔账

宽依赖的代价可以用传输量估计。设 $N$ 条记录、平均每条 $s$ 字节、集群节点数 $p$：

$$B_{\text{shuffle}} \approx N \cdot s \cdot \frac{p-1}{p}.$$

map 端**预聚合**（如 `reduceByKey`）把每节点本地同 key 记录先合并，$N$ 缩小为"每节点 distinct key 数之和"。例：1 亿条 `(user, count)`、100 万用户、20 节点：朴素 shuffle 传约 $10^8 \cdot s$ 字节；预聚合后只需约 $2 \times 10^6$ 条（100 万 key × 20 节点的部分聚合结果），**传输量降 50 倍**。这就是"能窄不宽、能聚合再 shuffle"的定量依据。

## 3.5 数据湖、数据仓库与湖仓一体

- **数据仓库（data warehouse）**：面向分析的关系型系统（Teradata、Snowflake、BigQuery）。schema-on-write：写入时强制 schema，数据干净、查询快，代价是所有数据入库前都要建模转换，原始异构数据难以容纳。
- **数据湖（data lake）**：把原始数据按原样（通常对象存储上的 Parquet/JSONL 文件）存放，schema-on-read，读取时各自解释。灵活廉价，代价是缺乏约束时沦为"数据沼泽"（data swamp）：无 schema、无血缘、无质量保证。
- **湖仓一体（lakehouse）**（Zaharia et al., CIDR 2021）：在数据湖的开放文件格式之上加一层**元数据与事务表格式**（Delta Lake、Apache Iceberg、Apache Hudi），提供 ACID 事务、schema 演化、时间旅行（查询历史版本——与第 4 章数据版本控制思想相通）、增量处理，让"一次存储、多种引擎"成为可能。

演进线索值得记住：数仓（强 schema，贵而干净）→ 湖（弱 schema，便宜而乱）→ 湖仓（开放存储 + 事务元数据）。AI 场景偏好湖仓：训练数据既有结构化表格也有图像/文本原始文件。

| 维度 | 数据仓库 | 数据湖 | 湖仓一体 |
|---|---|---|---|
| schema 策略 | schema-on-write | schema-on-read | 表格式管理下可演化 |
| 存储格式 | 私有/列存内部格式 | 开放文件（Parquet/JSONL） | 开放文件 + 事务元数据 |
| 事务与 ACID | 支持 | 基本不支持 | 支持（快照隔离/时间旅行） |
| 数据类型 | 结构化为主 | 结构化/半结构化/非结构化 | 全类型 |
| 典型风险 | 成本高、灵活性差 | 数据沼泽 | 元数据层运维复杂度 |
| 适合的 AI 场景 | BI 报表、特征明细 | 原始语料/图像存档 | 训练集版本化、特征回填 |

选型的经验法则：**已有强 schema 的结构化业务 → 数仓；海量不可预知形态的原始数据 → 湖；两者都要且团队撑得起元数据工程 → 湖仓**。对本书的 AI 项目而言，湖仓的"时间旅行"（查询数据的历史快照）与第 4 章 DVC 的版本思想一脉相承——前者在存储层解决，后者在流水线层解决，共同构成数据可追溯性的两块拼图。

## 3.6 流处理概念：Kafka 与窗口

### 3.6.1 Kafka：分布式提交日志

前面的技术都假设"数据先存成文件再批量处理"（批处理，batch）。当数据需要秒级可用（实时风控、监控告警），就需要流处理（streaming）。Apache Kafka 是事实标准的分布式消息系统，本质是**分布式、可持久化的提交日志（commit log）**：生产者把记录追加到主题（topic）的分区（partition）末尾，消费者按偏移量（offset）顺序读取，日志按保留期保留——消费不删除数据，因此同一份数据可以被多个下游（实时计算、落湖归档）重复消费。这把"数据的发布"与"数据的处理"解耦。

### 3.6.2 窗口：无界数据上的有界计算

流是无界的，聚合必须有界——窗口（windowing）定义了"对哪一段数据聚合"：

- **滚动窗口（tumbling）**：首尾相接、不重叠，如每 5 分钟的点击量；
- **滑动窗口（sliding）**：带步长地重叠滑动，如"最近 1 小时、每 5 分钟更新"的滑动平均；
- **会话窗口（session）**：按活动间隙动态切分（如用户 30 分钟无操作则断开），用于行为序列分析。

还有一个绕不开的语义问题：**事件时间（event time）与处理时间（processing time）不一致**——日志迟到、乱序是常态。按事件时间开窗就必须回答"窗口何时可以关闭"，现代系统（Google Dataflow 模型，Akidau et al., VLDB 2015）用水位线（watermark，"到达此时间戳的数据应已到齐"的进度承诺）加允许迟到（allowed lateness）处理。《模型部署与 MLOps》课程监控的实时特征，多数就是流处理窗口聚合的产物。

**一个手算的小例子**：事件时间 10:05 的记录 $a$ 因网络拥塞，在 10:09 才被处理端收到。若按处理时间开 [10:00,10:05) 的 5 分钟滚动窗口，$a$ 落进 [10:05,10:10) 窗口——错了窗。水位线策略：系统宣布"事件时间已推进到 10:07"（即承认最多迟到 2 分钟），[10:00,10:05) 窗口在水位线越过 10:05 后关闭；$a$（10:05）恰好踩线被拒或进入"允许迟到 5 分钟"的补偿更新。可见**窗口结果取决于水位线策略**：水位线太紧丢数据、太松窗口迟迟不出结果——这是流处理工程里最主要的调参对象。

**窗口语义小结**：滚动窗口适合固定周期报表与特征（每小时 UV）；滑动窗口适合平滑趋势（近 1 小时均值、每分钟更新）；会话窗口适合"以人为单位"的行为切分。三者都建立在同一条纪律上：**窗口边界由事件时间定义，结果发布由水位线控制**。

**批流结合的架构问题**：实践中常需要"实时看今天 + 夜间校正历史"两套计算——Lambda 架构用批、流两条管道分别计算再合并，代价是同一逻辑写两遍（第 2 章"训练-服务偏斜"的温床）；Kappa 架构干脆只留流管道，需要重算历史时把 Kafka 日志回放一遍。选择的关键不是技术潮流，而是你的团队养得起几条管道。

## 3.7 关键公式速查

| 公式 | 含义 | 适用条件 |
|---|---|---|
| $T_{\text{read}} \approx \text{数据量}/\text{有效带宽}$ | 顺序扫描时间下界 | 带宽取实际有效值（约为峰值的 50–80%） |
| $M \approx 2\text{–}6 \times |文件|$ | pandas 全量读取的内存放大系数 | 含字符串与日期列时取高值 |
| 布隆过滤器误报率：$p \approx (1 - e^{-kn/m})^k$ | 去重预过滤的内存-精度权衡 | $k$ 为哈希函数数、$n$ 元素数、$m$ 位数（《数据结构与算法》第 7 章） |
| 蓄水池采样：第 $i$ 个元素以 $1/i$ 概率替换当前样本 | 未知总量的等概率抽样 | 单遍扫描、内存 $O(s)$（《数据结构与算法》第 7 章） |
| reduceByKey 优于 groupByKey | map 端预聚合减少 shuffle 传输量 | 聚合函数满足结合律 |

## 3.8 示例与案例

### 案例 1（手算）：一笔 IO 账

任务：统计 500 GB 用户日志中每个用户的点击数。

- 方案 A（单机随机访问）：为每个用户在哈希表里累加。500 GB 约含 50 亿条记录，顺序扫描 SSD @ 1 GB/s 需约 500 s；但哈希表有 2000 万用户 × 计数器 ≈ 320 MB，可全驻内存，配合顺序读其实单机可行——**先算内存再下结论**，这正是 3.1 节的方法论。
- 方案 B（MapReduce）：map 阶段各节点处理 1/20 分片并本地 `reduceByKey` 预聚合（每片用户数≈2000 万×1/20，传输量骤降），shuffle 只传聚合结果而非原始记录。20 节点并行，扫描墙钟时间约 25–50 s，代价是部署一套集群。
- 结论：数据量 500 GB 属于**单机技术带**（方案 A/DuckDB）；当数据达到数十 TB 或作业需分钟级时效时，方案 B 的范式才划算。

### 案例 2（代码）已在 3.2.2 与 3.3.2 给出：格式基准测试与分块/DuckDB 等价性校验。请至少运行一次格式基准测试，把输出数字记录到你的学习笔记——第 99 章综合项目二将要求你把这一实验扩展成完整报告。

## 3.9 常见误区与陷阱

1. **"内存不够就加机器"**。很多时候一条 `dtype` 指定（int64→int32、category 类型）、一次列裁剪就能省一半内存。先做 3.1.1 节那笔账。
2. **把 CSV 当长期存储格式**。CSV 无类型、无统计信息、体积大、解析慢，且每次读取都要重新"猜"schema。归档与管道内部传输请用 Parquet，CSV 只留给人看与导出。
3. **在 Spark 里用循环与 collect**。把单机思维平移到集群（driver 端 `collect()` 大数据、Python 循环逐行处理）是分布式性能事故的头名来源。思考的单位应是"对整个分区的变换"。
4. **忽视 shuffle 成本**。随手一个 `groupBy` 可能触发全量网络传输。能 map 端预聚合就预聚合，能广播小表（broadcast join）就广播。
5. **流处理忽视乱序**。按处理时间开窗看似简单，但重放历史数据或上游延迟时会得到与事件时间完全不同的结果——监控指标会"漂"，风控特征会错。流式聚合必须明确 event time 与水位线策略。

## 3.12 进阶方向

- **查询优化器与执行引擎**：DuckDB/Spark 的向量化执行、代码生成与代价优化是数据库系统课的核心；需要补关系代数与 Volcano 迭代器模型。
- **流批一体（stream-batch unification）**：Flink 的真正事件时间语义与 kappa 架构（只用流处理一条管道服务批与流两种需求）；需要补充一致性快照与 exactly-once 的实现机制（Chandy-Lamport 思想）。
- **Serverless 数据湖查询**：基于对象存储的存算分离与缓存（Alluxio 类系统）；需要补分布式缓存与一致性哈希。
- **向量化数据库与列式的极限**：bit-packing、字典编码、zone map 等 Parquet 编码细节，可读 Parquet 官方规范与 Dremel 论文（Melnik et al., VLDB 2010，Parquet 嵌套列存的源头）。
