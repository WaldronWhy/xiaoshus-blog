# 第 2 章 知识图谱：结构化知识工程

> **本章定位**：第 1 章的逻辑给了我们"严格"，本章把严格的知识**规模化**——知识图谱（knowledge graph）是把世界的一部分写成海量三元组的工程化实践，是符号知识在工业界最成功的形态。它向上承接第 1 章（本体=受约束的一阶逻辑），向下支撑第 3 章（KGE 把三元组变成向量）与第 5 章（KG-RAG 把三元组喂给大模型）。前置：[《数据结构与算法·第 4 章》](/xiaoshus-blog/textbooks/ai/programming/data-structures/04/)。

## 2.0 本章学习目标

完成本章后，你应当能够：

1. 准确区分知识图谱中的**模式层（本体）**与**数据层（实例）**，并解释三元组 $(h, r, t)$ 中每部分的语义角色；
2. 读写 RDF 三元组与 Turtle 语法，编写基本的 SPARQL 查询（SELECT/FILTER/路径查询）；
3. 描述知识图谱构建流水线的四个阶段（抽取、清洗、对齐、融合），并说出实体对齐解决的核心问题；
4. 用 networkx 把一组三元组建成有向多重图，实现一阶查询、多跳查询与关系路径枚举；
5. 用图算法（最短路径、连通分量、中心性）对知识图谱做结构分析，并解释这些量与知识质量的联系。

## 2.1 什么是知识图谱

**定义（工作版）**：知识图谱是以**图**为数据结构、以**三元组**为基本单元、以**本体**为模式约束的知识库。一个三元组（triple）记作

$$
(h, r, t), \qquad h \in \mathcal{E} \text{（头实体）}, \quad r \in \mathcal{R} \text{（关系）}, \quad t \in \mathcal{E} \cup \mathcal{L} \text{（尾实体或字面值）}
$$

例如（创作, 吴承恩, 西游记）、（上映年份, 西游记, 1986）。与第 1 章对照：$Created(wuchengen, xiyouji)$ 是一阶逻辑原子，三元组是**只保留二元谓词、且谓词集固定**的原子——表达力的削减换取了存储、查询与学习的可行性。

两个层次：

- **模式层（schema / 本体，ontology）**：定义有哪些实体类型、哪些关系、关系的定义域与值域。如"创作"的定义域是"人物"、值域是"作品"。本体是一条形式化的约定，其逻辑底层是**描述逻辑（description logic, DL）**——一阶逻辑的可判定片段（见第 1 章拓展阅读）。
- **数据层（实例层）**：具体三元组，如（创作, 吴承恩, 西游记）。

**规模感的三个坐标**：WordNet（约 15 万词、语义网络先驱）、Freebase（约 4000 万实体、20 亿三元组，已归档）、Wikidata（公开、持续更新的自由许可知识图谱，是本章实验数据的推荐来源）。Google 于 2012 年提出 "Knowledge Graph" 术语并用之于搜索，此后工业界（Amazon Product Graph、阿里商品图谱等）大量跟进。

知识图谱回答的是第 1 章留下的"知识获取瓶颈"：手工写公理太贵，但**众包 + 自动抽取**可以规模化地生产二元事实。

## 2.2 RDF 与 SPARQL 概览

### 2.2.1 RDF：万物皆 URI

资源描述框架（Resource Description Framework, RDF）是 W3C 标准的 triples 数据模型：每条三元组的三个位置都是（全局唯一的）URI 或字面值，形如

```
ex:吴承恩  ex:创作  ex:西游记 .
ex:西游记  ex:体裁  "小说"^^xsd:string .
ex:吴承恩  rdf:type  ex:作家 .        # 类型陈述
```

要点：

1. **URI 消除歧义**：同名"西游记"（小说/电视剧/游戏）用不同 URI 区分——这比字符串匹配严格得多；
2. **rdf:type 陈述把实例挂到模式层**（"吴承恩是一个作家"）；
3. 序列化格式有 Turtle（上例，人类可读）、RDF/XML、JSON-LD。

### 2.2.2 SPARQL：图上的查询语言

SPARQL 之于 RDF，如同 SQL 之于关系表。核心是**图模式匹配**：把三元组中的位置换成变量（`?x`），查询引擎在图中找所有代入：

```sparql
# 问：孙悟空的师父的"体裁为小说"的作品里，谁创作了它？
# （演示变量穿越与过滤）
SELECT ?author WHERE {
  ?character  ex:师从    ?master .
  ?work       ex:主角    ?character .
  ?work       ex:体裁    ?genre .
  FILTER (?genre = "小说")
  ?author     ex:创作    ?work .
}
# 期望结果：吴承恩
```

SPARQL 1.1 支持**属性路径**（property path）表达任意跳数：`?x ex:师从+ ?y`（一跳或多跳的"师从"链），这正对应第 3 节要自己实现的多跳查询。

## 2.3 知识图谱构建：从文本到图谱

构建流水线四阶段（与[《自然语言处理·第 3 章》](/xiaoshus-blog/textbooks/ai/ai-core/nlp/03/)的信息抽取内容互为表里）：

### 2.3.1 实体抽取（NER）

从文本中识别实体mention并分类（人名/地名/机构/作品……）。经典方法是 BiLSTM-CRF 或 BERT+CRF（序列标注），见[《自然语言处理·第 3、5 章》](/xiaoshus-blog/textbooks/ai/ai-core/nlp/05/)。本课程不重复其细节，只强调其输出对图谱的意义：**节点候选**。

### 2.3.2 关系抽取（Relation Extraction）

对实体对 $(e_1, e_2)$ 判定关系类型（"创作"/"饰演"/无关系）。远程监督（distant supervision）思路：用已有图谱的三元组反向标注语料（图谱里有（创作，吴承恩，西游记），则所有同时含两实体的句子都弱标注为"创作"）——自动获得大量带噪训练数据，再用有监督模型降噪。

### 2.3.3 实体对齐（Entity Alignment / Disambiguation）

不同来源的 mention 指向同一现实实体的判定：文本里的"孙悟空"该挂到小说角色还是电视剧角色？经典方法两步走——**候选生成**（别名表、字符串相似度）+ **排序消歧**（上下文相似度）。跨语言图谱对齐（把中文 DBpedia 与 Wikidata 对齐）则是第 3 章嵌入方法的重要应用：两边的实体都嵌成向量后，对齐 = 找最近邻。

### 2.3.4 知识融合与质量

对齐后的三元组入库，还要做冲突检测（同一事实两个矛盾值）、冗余合并、模式一致性校验（"创作"的头实体必须是"人物"——这正是一条描述逻辑公理的检查）。工业图谱的长期成本几乎全在质量维护上。

## 2.4 用 networkx 构建与查询小型知识图谱

Python 生态中工程级 RDF 栈是 `rdflib`（含 SPARQL 引擎），本节先用 networkx 从零实现，让你看清"图谱查询 = 图遍历"的本质；工程上再切换到 rdflib。

```python
# pip install networkx
import networkx as nx

# ---------- 数据层：一组中文领域三元组（头, 关系, 尾） ----------
triples = [
    ("吴承恩",   "创作", "西游记"),
    ("西游记",   "体裁", "小说"),
    ("西游记",   "主角", "孙悟空"),
    ("孙悟空",   "物种", "猴"),
    ("孙悟空",   "师从", "菩提祖师"),
    ("六小龄童", "饰演", "孙悟空"),
    ("六小龄童", "职业", "演员"),
]

kg = nx.MultiDiGraph()          # 有向多重图：两实体间可有多种关系
for h, r, t in triples:
    kg.add_edge(h, t, relation=r)

def query_1hop(kg, entity, relation=None):
    """一阶查询：entity 的所有出边（可按关系过滤）。"""
    return [(entity, d['relation'], v)
            for _, v, d in kg.out_edges(entity, data=True)
            if relation is None or d['relation'] == relation]

def query_multi_hop(kg, src, rel_seq):
    """多跳查询：沿关系序列 rel_seq 逐跳扩展，返回可达实体集合。
       语义上等价于 SPARQL 的固定路径图模式。"""
    frontier = {src}
    for r in rel_seq:
        nxt = set()
        for e in frontier:
            for _, v, d in kg.out_edges(e, data=True):
                if d['relation'] == r:
                    nxt.add(v)
        frontier = nxt
    return frontier

print(query_1hop(kg, "孙悟空"))
print(query_multi_hop(kg, "六小龄童", ["饰演", "师从"]))   # 饰演的角色师从谁？

# 预期输出：
# [('孙悟空', '物种', '猴'), ('孙悟空', '师从', '菩提祖师')]
# {'菩提祖师'}
```

**多跳查询与可解释推理**：查询（六小龄童 --饰演--> ? --师从--> ?）得到"菩提祖师"，这条两跳路径本身就是**推理的解释**——"六小龄童饰演的角色师从菩提祖师"。路径枚举实现如下：

```python
def find_relation_paths(kg, src, dst, max_hops=3):
    """枚举 src 到 dst 全部不超过 max_hops 的关系路径（有向）。
       复杂度：路径数最坏 O(b^max_hops)，b 为平均出度——
       与第1章 SAT 的组合爆炸同源，故限制跳数。"""
    results = []
    def dfs(node, path):
        if len(path) >= max_hops and node != dst:
            return
        if node == dst and path:
            results.append(list(path))
            return
        for _, v, d in kg.out_edges(node, data=True):
            if (node, d['relation']) not in [(p[0], p[1]) for p in path]:
                path.append((node, d['relation'], v))
                dfs(v, path)
                path.pop()
    dfs(src, [])
    return results

print(find_relation_paths(kg, "吴承恩", "猴"))
# 预期输出：
# [[('吴承恩', '创作', '西游记'), ('西游记', '主角', '孙悟空'),
#   ('孙悟空', '物种', '猴')]]
```

这条 3 跳路径"吴承恩 —创作→ 西游记 —主角→ 孙悟空 —物种→ 猴"是知识图谱上最朴素的"推理"：**推理 = 在图上找路径**。第 3 章 KGE 的链接预测将把它变成"在向量空间里找最近的尾实体"，而第 5 章的 KG-RAG 会把这种路径作为证据喂给语言模型。

## 2.5 图结构分析：用图算法审计知识质量

在[《数据结构与算法·第 4 章》](/xiaoshus-blog/textbooks/ai/programming/data-structures/04/)学过的算法在这里全部有工程意义：

```python
# 承接上节 kg
import networkx as nx

ug = kg.to_undirected()                      # 无向视图做连通性分析
print("连通分量个数:", nx.number_connected_components(ug))
print("两实体间最短关系链:",
      nx.shortest_path(ug, "六小龄童", "小说"))
print("度最高的实体:", max(dict(kg.degree()).items(), key=lambda kv: kv[1]))
# 预期输出：
# 连通分量个数: 1
# 两实体间最短关系链: ['六小龄童', '孙悟空', '西游记', '小说']
# 度最高的实体: ('孙悟空', 3)
```

解读：**连通分量**暴露"孤岛实体"（对齐失败的典型症状——同一实体被建成两个不相连的节点）；**度分布**近似幂律是真实图谱的常态（头部实体如"中国"有数万条边）；**中心性**高的实体是知识库的"枢纽"，也是抽取错误的高发区（万物皆可错连到"美国"）。

## 2.6 关键公式速查

| 概念 | 形式化 | 说明 |
|---|---|---|
| 三元组 | $(h, r, t),\ h,t \in \mathcal{E},\ r \in \mathcal{R}$ | 二元化的一阶原子 |
| 图规模 | $\|\mathcal{G}\| = \|\mathcal{E}\| + \|\mathcal{R}\| +$ 三元组数 | 三大公开基准常用此口径 |
| SPARQL 图模式 | $P = \{(?x, r_1, ?y), (?y, r_2, ?z)\}$ | 查询 = 求所有使 $P \subseteq \mathcal{G}$ 的代入 |
| 路径查询 | $x \xrightarrow{r_1} \cdots \xrightarrow{r_k} y$ | SPARQL 属性路径 `r1/r2/.../rk` |
| 多跳查询复杂度 | 最坏 $O(b^k)$，$b$=平均出度，$k$=跳数 | 固定 $k$ 时对 $\|\mathcal{E}\|$ 线性 |
| 实体对齐（嵌入版，预告第 3 章） | $\arg\min_{e' \in \mathcal{E}'} \|\mathbf{e} - \mathbf{e}'\|$ | 跨图最近邻 |

## 2.7 示例与案例

### 案例 1（手算）：SPARQL 查询的代入过程

对 2.4 节的图谱执行查询 `SELECT ?m WHERE { ?a ex:饰演 ?c . ?c ex:师从 ?m . }`。逐步匹配：

1. 模式一 `?a ex:饰演 ?c`：图中仅一条匹配，$\theta_1 = \{a/\text{六小龄童},\ c/\text{孙悟空}\}$；
2. 在 $\theta_1$ 约束下匹配模式二 `?c ex:师从 ?m`：$\theta_2 = \{m/\text{菩提祖师}\}$；
3. 合并代入，输出 $m = $ 菩提祖师。

注意查询引擎做的是**从图出发找代入**（自底向上），而不是从问题出发搜索——这是数据库式查询与第 1 章定理证明的本质分工：查询回答"图里有什么"，证明回答"逻辑上必然有什么"。

### 案例 2（代码）：从非结构化文本到图谱的迷你流水线

不调用 NLP 模型，用规则模板模拟"抽取→建图→查询"全流程，体会流水线的形状：

```python
# pip install networkx（另需标准库 re）
import re
import networkx as nx

# 模拟"文本 + 抽取模板"。真实系统中此步由 NER+RE 模型完成
# （见《自然语言处理·第 3 章》），本例用句式模板代替。
texts = [
    "吴承恩创作了西游记。",
    "六小龄童饰演了孙悟空。",
    "孙悟空师从菩提祖师。",
]
templates = [("{p}创作了{o}。", "创作"),
             ("{p}饰演了{o}。", "饰演"),
             ("{p}师从{o}。", "师从")]

def extract(texts, templates):
    """对每句话尝试每个模板，抽出 (头, 关系, 尾)。"""
    out = []
    for t in texts:
        for tpl, rel in templates:
            fmt = tpl.format(p="(.+?)", o="(.+?)")   # 模板 -> 正则
            m = re.fullmatch(fmt, t)
            if m:
                out.append((m.group(1), rel, m.group(2)))
    return out

kg = nx.MultiDiGraph()
for h, r, t in extract(texts, templates):
    kg.add_edge(h, t, relation=r)

print("抽取到的三元组数:", kg.number_of_edges())
print("实体列表:", sorted(kg.nodes))
print("吴承恩的出边:", [(h, d['relation'], v)
                      for h, v, d in kg.out_edges('吴承恩', keys=False, data=True)])

# 预期输出：
# 抽取到的三元组数: 3
# 实体列表: ['六小龄童', '吴承恩', '孙悟空', '菩提祖师', '西游记']
# 吴承恩的出边: [('吴承恩', '创作', '西游记')]
```

这个玩具流水线暴露了真实系统的全部难点：模板覆盖不了语言变化（"西游记是吴承恩写的"就抽不出）、"孙悟空"既是文本实体又是角色实体（对齐问题）、抽取错了图谱就错（垃圾进垃圾出）。**知识工程的质量瓶颈从逻辑时代（手写公理）转移到了数据时代（抽取噪声），但从未消失。**

## 2.8 常见误区与陷阱

1. **把知识图谱当"图数据库"**。图数据库（Neo4j 等）是存储引擎，知识图谱是带本体约定的知识层。前者可以只存社交好友边，后者要求模式层约束与可追溯的出处（provenance）。
2. **忽视字面值与实体的区别**。（人口, 中国, "14亿"）的尾是字面值不是实体，KGE（第 3 章）通常只嵌入实体不嵌入字面值——把字面值嵌进去会引入无意义的相似度。
3. **同名实体直接合并**。字符串相等不等于实体相同（两个"西游记"），跳过对齐的图谱会悄悄长出错误连接，且事后极难清理。
4. **多跳查询不限跳数**。$O(b^k)$ 的组合爆炸在稠密图谱（真实图谱平均出度可达数十）上 $k=4$ 就可能亿级路径。工程上必须限跳数、剪枝或改用嵌入近似（第 3 章）。
5. **以为图谱是静态的**。真实世界事实会过期（官员任期、影片票房），图谱需要版本与时间戳（形如（任职, 某人, 某职, 起止时间）的四元组/N-ary 关系）。把时间压扁进二元组是工业图谱最常见的建模债。
